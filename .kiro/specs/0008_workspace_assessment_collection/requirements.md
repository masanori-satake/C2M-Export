# Requirements Document

## はじめに

C2M-Export は当初、「Confluence のあるページとその配下のページを 1 つの Markdown に統合し、利用者が自分のナレッジとして AI にインプットする」ツールとして提供を開始した。これを、最大で**ワークスペースレベル**で、保存されているページや添付ドキュメント等の状況を把握・分析し、他ストレージ（SharePoint / OneDrive 等）への**移設課題の抽出・計画立案**を支援するツールへと成長させる。

直前の spec `0007_agent_analysis_skill` は、この成長の第一歩として「エージェント（GitHub Copilot / Kiro / 汎用 Agent Skills / MCP）から状況把握・分析できる Skill」と、それを支える共通 1 層（`analysis/api.py:run_analysis` → CLI `python -m c2m_export.analyze`（stdout 純 JSON）/ MCP / `SKILL.md`）を確立した。0007 の分析は既存 `Collector`（親子 DFS）が返す `RawInventory` / `PageMeta` に閉じており、取得する情報は「ページ本文バイト長・添付メタ・個別アクセス制限・最終更新日時・マクロ名」に限られる。

本 spec（0008）は、その「全体把握・詳細調査」をより深く行うために、**Confluence REST API を走査して状況把握・分析に有用な情報を取得する収集層（I/O 層）を拡張する**ことを担う。利用者は**管理者特権を持たない一般ユーザー**を前提とする。取得対象は OpenAPI（Confluence DC 10.2.19）精査により、管理者権限を要さずに取得見込みのある API に限定する。

本 spec のスコープは「収集層の拡張」に寄せる。すなわち、下記 A〜D の REST API 情報を取得し、0007 が確立した JSON（`AnalysisResponse`）／レポートに**追加のみ・既定値付き・後方互換**で載せられるようにすることである。分析エンジン・JSON スキーマ・Skill/MCP の枠組みそのものは**作り直さず、0007 を再利用・拡張する**。

- **A. 走査効率・規模把握**: スペース一覧、子孫ページ総数プレビュー、カーソル走査（scan）、スペースメタ。ワークスペース/スペースの規模・構造の当たりをつける。
- **B. 移設課題抽出（鮮度・来歴・分類）**: 更新履歴（作成者・最終更新者・貢献者）、ラベル、CQL 検索、コメント、添付の抽出テキスト。
- **C. 権限・共有範囲**: 実効的な閲覧制限（継承含む）、スペース権限照会（GET 系）、ウォッチャー、実行ユーザーと所属グループ。
- **D. 環境コンテキスト**: アクセスモード、サーバ情報（バージョン）。

API 呼び出し回数の爆発を避けるため、収集を **2 段**に分ける。(1) **全体把握フェーズ**（軽量・広く）でスペース一覧・規模プレビュー・カーソル走査により当たりをつけ、(2) **詳細調査フェーズ**（重量・狭く）で重い収集を対象を絞って**オプトイン**で取得する。詳細調査フェーズの収集対象は、さらに次の 2 種に分かれる。

- **per-page（ページ単位）の重い収集**: 更新履歴・ラベル・コメント・ウォッチャー（コンテンツ単位）・実効閲覧制限・添付抽出テキスト。対象ページ数に比例して API 呼び出しが増える。
- **per-space（スペース単位）の収集**: スペース権限照会（GET 系）・スペースウォッチャー。スペース数に比例（ページ数には比例しない）し、解決済みスペース集合に対し**スペースごとに 1 回ずつ**呼ぶ。per-page の DFS ループの外で収集する。

この 2 段は README の推奨ワークフロー（分析 → ルール決定 → エクスポート）の「分析」をより精緻にする位置づけである。

管理者特権が無い前提のため、一部 API は 401/403/空/未対応となり得る。この場合も 0007 で確立した**部分成功 + `uncertainties` 報告**設計を全 API に適用し、「取れたら使う、取れなければ理由を記録して継続」とする。加えて「このトークンで見えている範囲」をレポートに明示し、権限不足で欠落しうる旨を注記して、移設計画の信頼性を担保する。

本 spec は既存 CLI（結合エクスポート / assess / fsexport / permexport）および 0007 の分析モードの挙動を破壊せず、新たな収集メソッド・スキーマフィールド・CLI/設定オプションとして**追加のみ**で実装する。姉妹プロジェクト（J2M-Export / G2M-Export）との CLI 引数・振る舞いの一貫性、および将来の Confluence Cloud 対応を見据えた拡張性（サーバ情報取得を含む）を維持する。

### 用語

- **ワークスペース**: 本 spec では「実行トークンで参照可能な Confluence インスタンス全体（複数スペースの集合）」を指す。
- **全体把握フェーズ（軽量）**: スペース一覧・子孫ページ総数プレビュー・カーソル走査（scan）など、低負荷な API で規模・構造の当たりをつける収集段。
- **詳細調査フェーズ（重量）**: 対象を絞って取得する収集段。既定では無効（オプトイン）。per-page（ページ単位）の重い API（更新履歴・ラベル・コメント・コンテンツウォッチャー・実効閲覧制限・添付抽出テキスト）と、per-space（スペース単位）の API（スペース権限照会・スペースウォッチャー）に分かれる。
- **per-page 収集 / per-space 収集**: 詳細調査フェーズのうち、ページ 1 件ごとに呼ぶものを per-page 収集、解決済みスペース集合に対しスペース 1 件ごとに 1 回呼ぶものを per-space 収集と呼ぶ。per-space 収集は DFS の内側ではなく外側で 1 回ずつ実行する。
- **実効閲覧制限**: 親からの継承を含め、そのページに実際に効いている閲覧制限（`relevantViewRestrictions`）。0007/既存が使う個別制限（`byOperation`）とは意味が異なる。
- **見えている範囲（可視範囲）**: 実行トークン（ユーザー）と所属グループ、参照可能なスペース一覧から機械的に把握できる「このトークンで分析可能な範囲」。
- **取得可否は実機依存**: 一般ユーザー権限・インスタンス設定・添付種別により、取得できる場合と 401/403/空/未対応となる場合があること。

### 既存機能で満たせる要件と新規実装が必要な要件の区別

0007 と同様、各受け入れ基準の冒頭に次の区分を明示する。

- **【既存】**: 0007 または既存コード（`ConfluenceClient` / `Collector` / `analyze_inventory` / `AnalysisResponse` 等）でほぼ満たせるもの。
- **【一部既存】**: 既存の骨格・契約は利用できるが、新規メソッド追加・フィールド追加・抽出ロジック追加が必要なもの。
- **【新規】**: 現状に該当する収集・解析・出力が存在せず、新規実装が必要なもの。

### 前提と仮定（曖昧性に対する明示的な仮定）

- 本 spec は**収集層の拡張**に責務を限定する。分析純粋関数・JSON スキーマ・Skill/MCP の「枠組み」は 0007 のものを再利用し、各 API 情報の集約・提示に必要な抽出関数とフィールドのみを追加する。
- 実装は 0007 が完了している（`analysis/`, `analyze.py`, `AnalysisResponse`, `AnalysisParams`, `AnalysisConfig`, `Collector` 拡張点, Skill/MCP）ことを前提とする。0008 はその上に積む。
- OpenAPI 上存在する API でも、一般ユーザーで安定取得できるかは環境依存であるため、取得可否が実機依存の API は基準にその旨を明記し、失敗を致命としない。
- 「ワークスペースレベルの把握」は、管理者 API（グローバル権限・監査・インスタンスメトリクス等）を使わず、`GET /rest/api/space` 一覧を入口とする範囲に限る。
- `schema_version` の運用は 0007 の確定事項（キー追加＝後方互換なマイナー更新、削除・リネーム・意味変更＝メジャー）に従う。本 spec のフィールド追加はすべてマイナー更新に収める。

## 要件

### 要件 1: 2 段収集（全体把握フェーズ / 詳細調査フェーズ）の分離と制御

**ユーザーストーリー:** 利用者として、まず軽量な API でワークスペース/スペースの規模・構造の当たりをつけ、必要なときだけ対象を絞って重い per-page 情報を取得したい。大規模環境で API 呼び出し回数が爆発しないようにしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 収集を「全体把握フェーズ（軽量）」と「詳細調査フェーズ（重量）」の 2 段に分離し、各段の実行可否を CLI/設定で制御できるようにする。
2. 【新規】THE システム SHALL 既定では全体把握フェーズ（軽量）のみを実行し、詳細調査フェーズの重い収集（per-page = 更新履歴・ラベル・コメント・コンテンツウォッチャー・実効閲覧制限・添付抽出テキスト、および per-space = スペース権限照会・スペースウォッチャー）は**既定で無効（オプトイン）**とする。
3. 【新規】THE システム SHALL 詳細調査フェーズで取得する情報を**種類ごとに個別にオン/オフ**できる手段（例: `--collect-history` / `--collect-labels` / `--collect-space-permissions` 等）を提供する。
4. 【一部既存】WHEN per-page の詳細調査が有効化される THEN システム SHALL 対象ページ集合を、全体把握フェーズまたは起点解決で得た範囲に基づき決定し、不要な全ページ一括の重い呼び出しを避ける。
5. 【新規】WHEN per-space の詳細調査（スペース権限照会・スペースウォッチャー）が有効化される THEN システム SHALL per-page の DFS ループの外で、解決済みスペース集合に対しスペースごとに 1 回ずつ収集し、同一スペースに対する多重呼び出しを避ける。
6. 【新規】THE システム SHALL この 2 段収集を README の推奨ワークフロー（分析 → ルール決定 → エクスポート）の「分析」段を精緻化するものとして位置づけ、ドキュメントに反映する。

### 要件 2: スペース一覧を起点としたワークスペースレベル把握（A）

**ユーザーストーリー:** 利用者として、実行トークンで参照可能なスペースの一覧（global/personal、current/archived）を取得し、ワークスペース全体の規模・構造の入口にしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `GET /rest/api/space`（`type` / `status` / `label` / `contentLabel` / `expand` / ページング）を呼び出し、参照可能なスペース一覧を全件取得する手段を提供する。
2. 【新規】THE システム SHALL 各スペースについて種別（global / personal）・状態（current / archived）・説明等のメタを `GET /rest/api/space/{spaceKey}?expand=` で取得できるようにする。
3. 【新規】WHERE スペース一覧を起点とする THE システム SHALL 0007 の起点解決（`root_page_ids` / `space_keys`）に「参照可能な全スペース」を供給する経路を**追加のみ**で設け、下流の分析・JSON 層を変更せずにワークスペースレベル分析を可能にする。
4. 【新規】THE スペース一覧・スペースメタ SHALL 取得可否が実機依存であることを前提に、取得失敗時は致命とせず `uncertainties` に記録して継続する。
5. 【新規】THE システム SHALL 取得したスペース一覧とそのメタを `AnalysisResponse` に**追加のみ・後方互換**で載せる（既存キーを変更しない）。

### 要件 3: 走査効率・規模プレビュー（A）

**ユーザーストーリー:** 利用者として、重い DFS 走査を始める前にスペース/ページ配下の規模を安価に見積もり、カーソル走査で低負荷に全件列挙したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `GET /rest/api/content/{id}/descendant/page/count` を呼び出し、子孫ページ総数を 1 リクエストで取得する規模プレビュー手段を提供する。
2. 【新規】THE システム SHALL `GET /rest/api/content/scan`（`spaceKey` / `type` / `status` / `expand` / `cursor` / `limit`）によるカーソルページングでスペース配下コンテンツを全件列挙する手段を提供する。
3. 【新規】THE システム SHALL `GET /rest/api/content/{id}/descendant/{type}`（`expand` / `limit` / `start`）により子孫を型指定でフラット列挙する手段を提供する。
4. 【一部既存】THE システム SHALL 既存 `Collector` の親子 DFS（`RawInventory` を返す契約）を変更せず、scan / descendant をその契約の内側で差し替え・補強できる構成とする（0007「将来拡張の余地」2 に乗る）。
5. 【新規】THE 規模プレビュー・scan・descendant SHALL いずれも取得可否が実機依存であることを前提に、失敗時は致命とせず `uncertainties` に記録して継続する。

### 要件 4: 更新履歴・来歴の取得（B）

**ユーザーストーリー:** 利用者として、各ページの作成者・最終更新者・貢献者・バージョン来歴を取得し、0007 の鮮度分析を「誰が」まで拡張し、オーナー不在ページを抽出したい。

#### 受け入れ基準

1. 【新規】WHEN 更新履歴収集が有効化される（詳細調査フェーズ・オプトイン）THEN システム SHALL `GET /rest/api/content/{id}/history?expand=lastUpdated,contributors,...` を呼び出し、作成者・最終更新者・更新日時・貢献者一覧を取得する。
2. 【一部既存】THE システム SHALL 取得した来歴を `PageMeta` に**追加のみ・既定値付き**で保持し、0007 の鮮度ユースケース（UC2）の個別一覧に「最終更新者」等を付与できるようにする。
3. 【新規】THE システム SHALL 作成者・最終更新者が取得できないページを「オーナー不明」として区別し、移設計画で注意が必要なページとして抽出できるようにする。
4. 【新規】IF 更新履歴の取得に失敗した THEN システム SHALL そのページをスキップせず他情報は維持したまま、来歴のみ欠落として `uncertainties` に件数を記録し継続する。

### 要件 5: ラベルの取得（B）

**ユーザーストーリー:** 利用者として、ページ/スペースのラベルを取得し、分類や移設グルーピングの手がかりにしたい。

#### 受け入れ基準

1. 【新規】WHEN ラベル収集が有効化される THEN システム SHALL `GET /rest/api/content/{id}/label`（`prefix` / `limit` / `start`）でページラベルを全件取得する。
2. 【新規】THE システム SHALL `GET /rest/api/space/{spaceKey}/labels` でスペースラベルを取得する手段を提供し、これは**全体把握フェーズ（既定 ON・スペースメタの一部）**として収集してスペースのラベル数を `SpaceMeta` に保持する（ページラベル収集 `collect_labels` のオプトインとは独立）。
3. 【一部既存】THE システム SHALL 取得したラベルを `PageMeta`（および必要に応じスペース情報）に**追加のみ・既定値付き**で保持し、ラベル別の件数集計や絞り込みに供する。
4. 【新規】THE ラベル収集 SHALL 取得失敗時に致命とせず `uncertainties` に記録して継続する。

### 要件 6: CQL 検索によるサーバ側課題抽出（B）

**ユーザーストーリー:** 利用者として、全件走査せずに `lastmodified` / `label` / `type` / `creator` 等の条件でサーバ側に直接問い合わせ、移設課題候補を効率的に抽出したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `GET /rest/api/content/search?cql=&expand=&limit=&start=` を呼び出し、CQL 条件に合致するコンテンツをページングで全件取得する手段を提供する。
2. 【新規】THE システム SHALL CQL の既定 `expand` を `history,space,version` として来歴・スペース・バージョンを併せて取得する。
3. 【新規】THE システム SHALL CQL 文字列を利用者が CLI/設定で指定できるようにし、サーバ側で課題候補（例: 長期未更新・特定ラベル）を直接問い合わせできるようにする。
4. 【新規】IF CQL がサーバに拒否される（構文不正・権限不足）THEN システム SHALL 現象・原因・対処方法を日本語で報告し、致命とせず `uncertainties` に記録して他収集を継続する（起点が CQL のみの場合は要件 11 の起点空判定に従う）。

### 要件 7: コメントの取得（B）

**ユーザーストーリー:** 利用者として、ページのコメント（inline / footer / resolved 状態）を取得し、未解決の意思決定や文脈を移設時に把握したい。

#### 受け入れ基準

1. 【新規】WHEN コメント収集が有効化される THEN システム SHALL `GET /rest/api/content/{id}/child/comment` を `depth=all` および `expand=extensions.location,extensions.resolution` で呼び出し、全コメントを取得する（ロケーション・未解決判定は `location` クエリ引数でなく `expand` で取得する。design §2.1）。
2. 【新規】THE システム SHALL コメントの総件数（`comment_count`）、および可能な範囲で未解決（未 resolved）件数（`unresolved_comment_count`）とロケーション別件数（inline = `inline_comment_count` / footer = `footer_comment_count`）を集計し、`PageMeta` に**追加のみ・既定値付き**で保持する。
3. 【新規】WHERE Confluence DC のバージョンや応答により resolved 状態またはロケーション区分が判別できない THE システム SHALL 当該の内訳フィールド（`unresolved_comment_count` / `inline_comment_count` / `footer_comment_count`）を `None`（不明）として保持し、総件数 `comment_count` は可能な限り集計を継続する。
4. 【新規】THE コメント収集 SHALL 取得失敗時に致命とせず `uncertainties`（`comment_failed_count`）に記録して継続する。

### 要件 8: 添付の抽出テキスト取得（B）

**ユーザーストーリー:** 利用者として、添付の抽出テキストを取得し、0007 の「添付あり・本文がほぼ空」（UC5）のページで、添付の中身の概要を把握したい。

#### 受け入れ基準

1. 【新規】WHEN 添付抽出テキスト収集が有効化される THEN システム SHALL `GET /rest/api/content/{id}/child/attachment/{attachmentId}/extractedtext?limit=` を呼び出し、添付の抽出テキスト（またはその有無・長さ）を取得する。
2. 【新規】THE システム SHALL 抽出テキストの有無・長さ（概算）を添付メタ（`AttachmentMeta`）に**追加のみ・既定値付き**で保持し、本文補完判断の材料にできるようにする。
3. 【新規】THE 抽出テキスト収集 SHALL 添付種別・インスタンス設定により未対応/空になり得ることを前提に、取得失敗・空を致命とせず `uncertainties` に記録して継続する（取得可否は実機依存）。
4. 【新規】WHERE 大量添付がある THE システム SHALL 抽出テキスト取得を詳細調査フェーズのオプトインに限定し、対象を絞れるようにする（要件 1 と整合）。

### 要件 9: 実効閲覧制限の取得（C）

**ユーザーストーリー:** 管理者権限を持たない利用者として、親からの継承を含めてページに実際に効いている閲覧制限を把握し、移設時のアクセス範囲再現に役立てたい。

#### 受け入れ基準

1. 【新規】WHEN 実効閲覧制限収集が有効化される THEN システム SHALL `GET /rest/api/content/{id}/restriction/relevantViewRestrictions` を呼び出し、継承を含む実効的な閲覧制限を取得する。
2. 【既存】THE システム SHALL 既存の個別制限（`byOperation`、0007 UC3 が利用）と実効制限が**意味が異なる**ことを出力キー名・ドキュメントで区別する。
3. 【一部既存】THE システム SHALL 取得した実効閲覧制限を `PageMeta` に**追加のみ・既定値付き**で保持し、0007 の権限ユースケース（UC3）と併記できるようにする。
4. 【新規】THE 実効閲覧制限収集 SHALL 取得可否が実機依存であることを前提に、失敗時は致命とせず `uncertainties` に記録して継続する。

### 要件 10: スペース権限照会・ウォッチャー・実行ユーザー情報（C）

**ユーザーストーリー:** 利用者として、スペース権限（GET 系）・ウォッチャー・実行ユーザーと所属グループを取得し、利害関係者の推定と「このトークンで見えている範囲」の自己診断を行いたい。

#### 受け入れ基準

1. 【新規】WHEN スペース権限照会が有効化される（`collect_space_permissions`・詳細調査フェーズ・per-space）THEN システム SHALL スペース権限照会の GET 系エンドポイント（DC の実在パス。例 `GET /rest/api/space/{spaceKey}/permission`。実機で GET 系の実在パスを確認して採用）を、解決済みスペース集合に対しスペースごとに 1 回ずつ呼び出す手段を提供する。
2. 【新規】THE システム SHALL スペース権限照会が**一般ユーザーで読める範囲は環境依存**であり、DC バージョンにより GET 系エンドポイントが未対応の場合があることを前提に、403/未対応/空を致命とせず、当該スペースを `space_permission_failed_keys` に記録し `uncertainties` と `unavailable_apis`（`space_permissions`）に反映して継続する（取得可否は実機依存）。
3. 【新規】WHEN コンテンツウォッチャー収集が有効化される（`collect_watchers`・per-page）THEN システム SHALL `GET /rest/api/content/{contentId}/watchers` をページ単位で呼び出し、ページの利害関係者（移設連絡先の推定）を取得する。
4. 【新規】WHEN スペースウォッチャー収集が有効化される（`collect_watchers`・per-space）THEN システム SHALL `GET /rest/api/space/{spaceKey}/watchers` を解決済みスペース集合に対しスペースごとに 1 回ずつ（per-page の DFS ループの外で）呼び出し、スペースの利害関係者を取得する。
5. 【新規】THE ウォッチャー収集（コンテンツ単位・スペース単位の双方）SHALL 取得可否が実機依存であることを前提に、失敗時は致命とせず、コンテンツ単位は `content_watcher_failed_refs`、スペース単位は `space_watcher_failed_keys` に記録し `uncertainties` と `unavailable_apis`（`watchers`）に反映して継続する。
6. 【新規】THE システム SHALL `GET /rest/api/user/current?expand=` および `GET /rest/api/user/memberof` を呼び出し、実行ユーザーと所属グループを取得する（全体把握フェーズ・既定 ON）。
7. 【新規】THE システム SHALL スペース権限照会・スペースウォッチャーを詳細調査フェーズの per-space オプトイン、コンテンツウォッチャーを per-page オプトインとして扱い、管理者 API（グローバル権限 PUT 等）は一切呼び出さない。

### 要件 11: 「見えている範囲」の自己診断と明示（C）

**ユーザーストーリー:** 管理者特権を持たない利用者として、「このトークンで見えている範囲」を把握し、権限不足で情報が欠落しうる旨を移設計画の前提として明示したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 実行ユーザー（`user/current`）・所属グループ（`user/memberof`）・参照可能スペース一覧（`space`）から「このトークンで分析可能な可視範囲」を構成し、`AnalysisResponse` に**追加のみ・後方互換**で出力する。
2. 【新規】THE システム SHALL 可視範囲の出力に「管理者特権が無いため、権限により見えないページ/スペースは本結果に含まれない可能性がある」旨の注記を含める。
3. 【新規】THE システム SHALL 取得できなかった（403/空/未対応だった）API の種類を可視範囲の自己診断に反映し、どの情報が欠落しているかを機械可読に示す。
4. 【新規】IF 全起点（全 `root_page_ids` + 全 `space_keys` + 指定時の CQL/全スペース供給）の解決結果が空になる THEN システム SHALL 現象・原因・対処方法を日本語で報告し、0007 の `TARGET_NOT_FOUND`（終了コード 4）で終了する。

### 要件 12: 環境コンテキストの取得（D）

**ユーザーストーリー:** 利用者として、インスタンスの状態（読み取り専用モード等）と Confluence バージョンを取得し、API 差異判定や将来の Cloud 対応の布石にしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `GET /rest/api/accessmode` を呼び出し、読み取り専用モード等のインスタンス状態を取得する。
2. 【新規】THE システム SHALL `GET /rest/api/server-information` を呼び出し、Confluence バージョン等のサーバ情報を取得する。
3. 【新規】THE システム SHALL 取得した環境コンテキストを `AnalysisResponse` に**追加のみ・後方互換**で載せ、将来の API 差異判定・Cloud 対応の手がかりにできるようにする。
4. 【新規】THE 環境コンテキスト収集 SHALL 取得失敗時に致命とせず `uncertainties` に記録して継続する。

### 要件 13: 部分成功・取得可否の実機依存・エラー分類の踏襲

**ユーザーストーリー:** 利用者として、権限で取れない API があっても分析全体が止まらず、取れた情報は使い、取れなかった理由は記録される実行をしたい。

#### 受け入れ基準

1. 【既存】THE システム SHALL A〜D の各 API 呼び出しに 0007 の部分成功設計（失敗はスキップして継続し、`uncertainties` に件数・識別子を記録）を適用する。
2. 【既存】THE システム SHALL 401/403 を `AUTH_FAILED`、404 を `TARGET_NOT_FOUND`、その他 4xx・リトライ後も解消しない 5xx・ネットワークを `API_ERROR` に分類する 0007 の例外 → エラーコード規約（`confluence.py` の `requests.exceptions.HTTPError` の `response.status_code` 分類）を踏襲する。
3. 【新規】THE システム SHALL 取得可否が実機依存の API（実効閲覧制限・スペース権限照会 GET・ウォッチャー・添付抽出テキスト等）について、403/空/未対応を**致命的な `AUTH_FAILED` に昇格させず**、当該情報のみ欠落として `uncertainties` に記録する（起点解決そのものの 401/403 は従来どおり致命）。
4. 【既存】THE システム SHALL 5xx / ネットワークエラーに対し既存 `ConfluenceClient._request` の指数バックオフリトライを踏襲する。
5. 【既存】THE システム SHALL 個別ページ/添付の取得失敗時にそのページ/添付をスキップし、スキップ件数と識別子を集計・報告して全体を継続する。

### 要件 14: 0007 スキーマ・枠組みへの後方互換な追加

**ユーザーストーリー:** 既存利用者・既存エージェントとして、0008 で情報が増えても 0007 の JSON 出力・Skill/MCP が壊れないようにしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL A〜D の新規情報を `PageMeta` / `AttachmentMeta` / `RawInventory` / `AnalysisResponse` に**追加のみ・既定値付き**で載せ、既存フィールドの型・名称・順序・意味を変更しない。
2. 【既存】THE システム SHALL キー追加を `schema_version` のマイナー更新（例 `1.0` → `1.1`）として扱い、削除・リネーム・意味変更（メジャー更新）を本 spec では行わない（0007 確定事項に従う）。
3. 【新規】THE システム SHALL 新規分析（来歴・ラベル・コメント・実効制限・抽出テキスト・可視範囲・環境コンテキスト等）を 0007 の共通 1 層 `run_analysis` と `AnalysisResponse` の拡張として実装し、新しい分析エンジン・新 Skill/MCP を作り直さない。
4. 【新規】THE システム SHALL 新規収集情報の集約・提示に必要な抽出ロジックを API 非依存の純粋関数として実装し、API モック不要で単体テスト可能にする。
5. 【既存】WHEN 本機能を追加する THEN システム SHALL 0007 の Skill 定本（`skills/confluence-analysis/SKILL.md`）と複製（`.github/skills/` / `.kiro/skills/`）、MCP サーバの記述を新 API・新フェーズ・新オプションに合わせて更新する。

### 要件 15: CLI/設定の拡張（2 段収集・情報オン/オフ・CQL・スペース起点）

**ユーザーストーリー:** 利用者として、どのフェーズ・どの情報を取得するかを CLI/設定で制御し、CQL やスペース起点も指定したい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL 0007 の `AnalysisConfig` / `AnalysisParams` を**拡張（追加のみ）**し、2 段収集の制御・各情報のオン/オフ・CQL・スペース一覧起点のパラメータを追加する（新設の独立 Config は作らず既存を拡張する）。
2. 【新規】THE システム SHALL 詳細調査フェーズの各情報について、個別の有効化フラグ（per-page: `--collect-history` / `--collect-labels` / `--collect-comments` / `--collect-watchers` / `--collect-effective-restrictions` / `--collect-extracted-text`、per-space: `--collect-space-permissions`。なお `--collect-watchers` はコンテンツ単位とスペース単位の双方を有効化する）と、一括有効化手段（例: `--deep` 相当）を提供する。
3. 【新規】THE システム SHALL CQL 文字列（`--cql`）と「参照可能な全スペースを起点にする」オプション（例: `--all-spaces`）を提供する。
4. 【既存】THE システム SHALL 設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決し、トークンの環境変数（`C2M_CONFLUENCE_TOKEN` / `CONFLUENCE_TOKEN`）運用を踏襲する。
5. 【新規】THE システム SHALL 新設フラグの**既定を「軽量・無効」**に揃え、何も指定しなければ全体把握フェーズのみが走る後方互換な挙動とする。

### 要件 16: ドキュメント・ログ・一貫性（非機能）

**ユーザーストーリー:** 利用者として、新機能を既存ツールと一貫した日本語ログ・ドキュメントで扱い、認証情報が漏れない安全な実行をしたい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 人間向けログ・コメント・docstring を日本語（PEP 257 準拠）で記載し、エラーメッセージを「現象・原因・対処方法」構成とする。
2. 【既存】WHERE 機械可読 JSON モード THE システム SHALL 日本語ログを stdout 以外（stderr）へ振り分け、stdout の JSON と混在させない。
3. 【既存】THE システム SHALL 認証トークンを新規 API のログ・JSON 出力・エラーオブジェクト・Skill 定義に一切含めない（0007 の多層サニタイズを新経路にも適用する）。
4. 【既存】WHEN 本機能を追加する THEN システム SHALL `README.md` / `README_DEV.md` / `c2m_config_sample.yaml` / `.kiro/steering/*.md` を更新し、2 段収集・新 API・新キー・新オプションを反映する。
5. 【既存】THE システム SHALL 新規収集メソッドのページング・リトライを既存 `ConfluenceClient` 方針（全件ページング・指数バックオフ・Proxy）に揃える。

## スコープ外

本 spec は「ワークスペース状況把握・詳細調査のための収集層（I/O）拡張」と、その情報を 0007 の分析/JSON/Skill に後方互換で載せることに限定する。以下は対象外とする。

- **0007 で実装済みの分析基盤の作り直しをしない**: 共通 1 層 `run_analysis`・`AnalysisResponse` スキーマ骨格・Skill/MCP 枠組みを再設計・再実装しない。0008 は収集メソッド・フィールド・抽出純粋関数・CLI オプションの**追加のみ**で実現する。
- **権限の自動適用をしない**: 取得した実効閲覧制限・スペース権限を配置先ストレージへ自動適用しない（0007 と同じ方針）。
- **実エクスポート出力をしない**: 本 spec の収集・分析はファイルシステムへの実エクスポート・添付バイナリのダウンロード・差分同期/レジュームを行わない（既存 fsexport / sync の責務）。本 spec は読み取り専用・冪等。
- **管理者機能・管理者 API を使わない**: `/rest/api/admin/*`、`backup-restore/*`、グローバル `permissions`（PUT 系含む）、`index/reindex`、`webhooks`、`cluster/nodes`、`audit`、`instance-metrics` は対象外。
- **Confluence Cloud の実装はしない**: サーバ情報取得で将来の布石は置くが、Cloud 固有 API への対応実装は本 spec では行わない。
- **数値性能目標は設けない**: 0007 と同じく想定最大ページ数・許容実行時間の数値目標は設定せず、2 段収集・ページング・`limit` 上位 N・`truncated` 報告で過大負荷/出力を抑える。
