# Requirements Document

## はじめに

本機能は、Confluence 内のワークスペース状況を**エージェント（GitHub Copilot / Kiro / 汎用 Agent Skills / MCP）から把握・分析できるようにする Skill**を C2M-Export に追加し、そのために必要な **CLI の改善**を行うものである。

既存の assess モード（spec `0003_confluence_assessment`）は、規模・構造・移設リスク・権限・鮮度を集計し、Markdown / JSON の**レポートファイル**として出力する。しかしその出力は「集計値（カウント・分布・サマリ）」が中心であり、「ある条件に合致した**個別ページ/添付の一覧**」をエージェントが機械可読に受け取る口は（移設リスク項目を除き）存在しない。また、構造化データは常にファイルへ書き出され、**stdout へ純粋な機械可読 JSON を返すモード**は無い。

本 spec は、この 2 つの不足（個別一覧の提供・stdout への機械可読 JSON 返却）を中心に CLI を拡張し、その CLI をエージェントがサブプロセスとして安全に呼び出せる **Skill 定義**を整備することを目的とする。利用者が従来どおり CLI を直接利用するユースケースは維持する（後方互換）。

想定する利用形態の優先順位は次のとおりである。

1. **最優先: ローカル Skill**。ローカルに Python（3.8 以上）が導入済みで、本リポジトリがチェックアウト済みであることを前提に、Skill が CLI をサブプロセスとして起動する。対象ランタイムは **GitHub Copilot** と **Kiro** の両方。
2. **汎用 Agent Skills 形式**（`SKILL.md` + 補助スクリプト/指示書のディレクトリ構成）。OSS としての汎用性のために提供する。
3. **MCP サーバ**（ローカル Skill より低優先）。共有 PC への構成が容易に実現できる場合に提供する。

本機能は既存 CLI（結合エクスポート / assess / fsexport / permexport / 権限エクスポート）の挙動を破壊せず、新たなモード/フラグ/成果物として追加する。姉妹プロジェクト（J2M-Export / G2M-Export）との CLI 引数・振る舞いの一貫性、および将来の Confluence Cloud 対応を見据えた拡張性を維持する。

### 用語

- **Skill**: エージェント（GitHub Copilot / Kiro / 汎用 Agent Skills）が特定タスクを実行するために参照する指示書・補助スクリプトの集合。本 spec では C2M-Export の CLI を呼び出して Confluence の状況分析を行うためのものを指す。
- **ローカル Skill**: ローカル環境の Python と本リポジトリのチェックアウトを前提に、CLI をサブプロセス起動して結果を得る形態の Skill。
- **MCP サーバ**: Model Context Protocol に準拠し、分析機能をツールとしてエージェントに公開するサーバ。
- **機械可読 JSON（stdout）**: エージェントが直接パースできるよう、ログや進捗表示を混ぜず、標準出力に単独で返す構造化 JSON。
- **軽量サマリモード / 詳細モード**: 集計値のみを返すモードと、条件に合致した個別ページ/添付の一覧を返すモードの区別。
- **分析ユースケース**: 本 spec が対象とする 6 件の問い合わせ（移行リスク / 古いページ / 個別権限ページ / 圧縮ファイル / 添付あり空ページ / マクロ統計）。
- **個別一覧**: 条件に合致した各ページ/添付を、識別子（page_id / 添付名）とともに列挙したリスト。従来の「件数のみ」の集計と区別する。

### 既存機能で満たせる要件と新規実装が必要な要件の区別

本 spec の受け入れ基準では、調査ノート（`_research_notes.md`）の切り分けを反映し、各要件・各基準の冒頭または末尾に次の区分を明示する。

- **【既存】**: 既存コード（assess / permexport の既存データ・純粋関数）でほぼ満たせるもの。提示加工のみ必要な場合を含む。
- **【一部既存】**: 既存データは揃っているが、集約・交差判定・カテゴリ定義などのロジック追加が必要なもの。
- **【新規】**: 現状コードに該当する収集・解析・出力が存在せず、新規実装が必要なもの。

### 決定事項（設計フェーズおよびユーザー承認で確定済み）

当初の未確定事項は、design.md の「確定事項」節とユーザー承認により次のとおり確定した。詳細根拠は design.md を参照。

- **stdout への機械可読 JSON 返却の実現方式**: 専用エントリーポイント `python -m c2m_export.analyze` を新設（既存 assess は不変）。
- **個別一覧の提供元**: assess の `raw_inventory.pages[].restriction` ほか `PageMeta` から抽出する（permexport の別収集経路は使わない）。
- **圧縮形式カテゴリの拡張子集合**: 既定 `{zip, 7z, rar, gz, tar, bz2, xz, tgz, lzh, cab}`（`iso` / `dmg` は既定に含めない）、`--archive-ext` で上書き可。複合拡張子は末尾トークン抽出（`tar.gz` → `gz`）。
- **マクロ使用統計の収集方式**: collector が `body.storage` を解析してマクロ名を集計（converter 不変）。手作業修復候補は converter の方針を写像した静的テーブルで判定。
- **認証トークンの環境変数**: `C2M_CONFLUENCE_TOKEN`（主）/ `CONFLUENCE_TOKEN`（互換）。優先順位は CLI `--token` > 環境変数 > YAML。CLI 直接指定は非推奨。
- **Skill 定義フォーマット / MCP 配布形態**: GitHub Copilot / Kiro / 汎用 Agent Skills は `SKILL.md` オープン標準に一本化し、`skills/confluence-analysis/` を正本として `.github/skills/` と `.kiro/skills/` に複製。MCP は公式 `mcp`（FastMCP）・stdio 既定・optional 依存（`requirements-mcp.txt`、遅延 import）。
- **大規模時のサイズ上限・ページング・上位 N**: 数値性能目標は設けず、全件ページング収集＋ detail は `limit` 既定 1000 で上位 N 抽出＋ `truncated` / `total_count` 報告。UC 単位の早期打ち切りは行わない。
- **`schema_version`**: 初期 `"1.0"`、後方互換を壊す変更時のみメジャーを上げる運用。
- **`--stale-years`**: 追加する（`--stale-days` 併存、両指定時は `--stale-days` 優先、`years×365` の閏年非考慮近似、実効値を `stale_threshold_days` に明示）。

## 要件

### 要件 1: 機械可読 JSON を stdout に返すモードの提供

**ユーザーストーリー:** エージェント利用者として、分析結果をログや進捗表示と混在しない純粋な JSON として標準出力で受け取り、追加のファイル読み取りなしに直接パースしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 分析結果を、ログ・進捗・装飾を含まない機械可読 JSON として stdout に単独で出力するモードを提供する。
2. 【新規】WHEN 機械可読 JSON モードが指定される THEN システム SHALL 進捗・情報ログを stdout 以外（例: stderr）へ振り分け、stdout には JSON のみを出力する。
3. 【新規】THE システム SHALL 出力する JSON を、キーが安定した構造（バージョン識別子を含む）として定義する。
4. 【新規】WHEN 機械可読 JSON モードが指定されない THEN システム SHALL 既存 assess のファイル出力（Markdown / JSON）挙動を変更しない（後方互換）。
5. 【一部既存】THE システム SHALL 既存の `AssessmentResult` / `generate_json_report` が生成する構造化データを再利用し、stdout 出力でも同等のキー構造を保つ。

### 要件 2: 軽量サマリモードと詳細（個別一覧）モードの切り分け

**ユーザーストーリー:** エージェント利用者として、まず全体像を軽量なサマリで把握し、必要に応じて条件に合致した個別ページ/添付の一覧を取得したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 集計値（カウント・分布・サマリ）のみを返す軽量サマリモードを提供する。
2. 【新規】THE システム SHALL 条件に合致した個別ページ/添付の一覧を返す詳細モードを提供する。
3. 【新規】WHEN 詳細モードが要求される THEN システム SHALL 各項目について識別子（page_id / 添付名）と、そのページの URL または相対パスを含める。
4. 【新規】WHERE 大量の項目が該当する THE システム SHALL 件数上限または上位 N 抽出の手段を提供し、出力が過大になることを防ぐ（既定は設計で確定）。
5. 【一部既存】THE システム SHALL 個別一覧の生成に `AssessmentResult.raw_inventory.pages`（収集済み全 `PageMeta`）を活用する。

### 要件 3: 分析ユースケース (1) 移行リスクが高いページ一覧

**ユーザーストーリー:** 利用者として、移行時につまずきそうなページを、リスク理由とともに一覧で把握したい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 移設リスク項目（`risk_type` ∈ {PATH_LENGTH, INVALID_CHAR, BLOCKED_EXT, LARGE_FILE, DUPLICATE_NAME}）を、対象（page_id / 添付名 / パス）と理由とともに一覧として返す。
2. 【一部既存】THE システム SHALL 同一ページに複数のリスクがある場合、ページ単位でリスクを集約した一覧を返せる。
3. 【一部既存】THE システム SHALL リスク一覧をリスク件数または種別で並べ替え、上位 N を抽出できる。
4. 【既存】THE システム SHALL リスク種別ごとの件数サマリ（`risk_summary_counts` 相当）を併せて返す。

### 要件 4: 分析ユースケース (2) 直近 N 年更新されていない古いページの個別一覧

**ユーザーストーリー:** 利用者として、長期間更新されていないページを個別に一覧化し、移設対象から外す判断材料にしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 最終更新日から一定期間（可変しきい値）以上経過したページを、page_id / title / 最終更新日とともに個別一覧として返す。
2. 【一部既存】THE システム SHALL 経過期間のしきい値を設定で変更可能にする（既存 `stale_days` を踏襲し、期間を「年」でも指定できることを設計で確定）。
3. 【既存】THE システム SHALL 併せて長期未更新ページの件数（`stale_page_count` 相当）および更新日分布（`freshness_distribution` 相当）を返す。
4. 【新規】IF ページの最終更新日が取得できない（`last_modified` が None）THEN システム SHALL そのページを「不明」として区別し、古いページ一覧に混入させない。

### 要件 5: 分析ユースケース (3) 個別権限が設定されているページ一覧

**ユーザーストーリー:** 管理者として、親からの継承ではなく個別のアクセス制限が設定されているページを一覧で把握したい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL 個別のアクセス制限を持つページ（`has_explicit=True` 相当）を、page_id / title / URL または相対パスとともに個別一覧として返す。
2. 【一部既存】THE システム SHALL 各ページについて Read 権 / Read+Write 権の区別と、登場するユーザー/グループを返す。
3. 【既存】THE システム SHALL 既存 permexport の `PagePermission`（ページ単位の権限一覧）を活用するか、assess の `raw_inventory.pages[].restriction` から抽出する方式のいずれかを採用する（どちらを採るかは設計で確定）。
4. 【既存】THE システム SHALL 権限分析の有効/無効を設定で切り替え可能にする（既存 `analyze_restrictions` を踏襲し、大規模時の API 負荷を考慮）。
5. 【既存】IF 権限情報の取得に失敗した THEN システム SHALL 分析を中断せず、取得失敗の件数を報告する。

### 要件 6: 分析ユースケース (4) 圧縮形式ファイルの個数と概算合計サイズ

**ユーザーストーリー:** 利用者として、zip / 7z / rar / gz / tar 等の圧縮形式ファイルが何個あり、概算で合計どの程度のサイズかを把握したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 圧縮形式カテゴリに属する拡張子集合（例: zip, 7z, rar, gz, tar 等。既定値は設計で確定）を定義する。
2. 【一部既存】THE システム SHALL 圧縮形式カテゴリに該当する添付の個数と概算合計サイズを、既存 `extension_summary`（extension / count / total_size）を基に集計して返す。
3. 【新規】THE システム SHALL `tar.gz` 等の複合拡張子の扱い（末尾トークンのみ抽出する現状挙動を踏まえた判定方針）を明示する。
4. 【新規】THE システム SHALL 圧縮形式カテゴリに含める拡張子集合を設定で上書き可能にする。
5. 【既存】IF サイズメタデータが欠落している添付が存在する（`file_size=None`）THEN システム SHALL その件数を報告し、概算合計サイズから除外されている旨を明示する。

### 要件 7: 分析ユースケース (5) 添付あり かつ 本文がほぼ空のページ

**ユーザーストーリー:** 利用者として、添付は存在するが本文がほとんど無いページを把握し、移設時の扱い（本文補完・添付の別管理等）を検討したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 「添付 1 件以上（`len(attachments) > 0`）かつ 本文が極小（`body_bytes < min_body_bytes`）」の交差条件に合致するページの個数を集計する。
2. 【新規】THE システム SHALL 上記交差条件に合致するページを、page_id / title / 添付件数 / `body_bytes` とともに個別一覧として返す。
3. 【一部既存】THE システム SHALL 本文の極小判定しきい値を設定で変更可能にする（既存 `min_body_bytes` を踏襲）。
4. 【新規】THE システム SHALL 本ユースケースが既存の `empty_page_count`（添付有無を考慮しない本文のみの件数）とは別物であることを、出力キー名等で区別する。

### 要件 8: 分析ユースケース (6) マクロ使用統計と手作業修復候補

**ユーザーストーリー:** 利用者として、Confluence でどのマクロがどれだけ使われており、Markdown 変換時に手作業での修復が必要そうなマクロはどれかを把握したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `body.storage`（XHTML）を解析し、structured-macro の `ac:name` および legacy `conf-macro` の `data-macro-name` を集計して、マクロ名別の使用回数を返す。
2. 【新規】THE システム SHALL マクロ使用統計を使用回数で降順に並べて返す。
3. 【新規】THE システム SHALL converter の変換方針（情報破棄＝空文字化されるマクロ、近似変換で整形劣化しうるマクロ、外部依存で再生成が必要なマクロ）に基づき、手作業修復候補となるマクロを区別して抽出する。
4. 【新規】THE システム SHALL 各マクロについて、手作業修復候補に該当する場合はその理由（内容欠損 / 近似変換 / 外部依存等の区分）を併せて返す。
5. 【新規】IF 本文の解析に失敗したページが存在する THEN システム SHALL そのページをスキップし、解析失敗の件数を報告して全体の集計は継続する。

### 要件 9: 非対話・冪等な実行

**ユーザーストーリー:** エージェント利用者として、Skill から CLI を呼び出す際に、対話プロンプトで止まらず、既定で破壊的操作を行わない安全な実行をしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 分析（本 spec のモード）実行時に、標準入力を要求する対話プロンプトを一切出さない。
2. 【既存】WHEN 分析モードが実行される THEN システム SHALL Confluence への書き込みおよび添付バイナリのダウンロードを行わない（既存 assess 方針を踏襲）。
3. 【新規】THE システム SHALL 既定で破壊的操作（既存ファイルの無確認上書き等）を行わず、上書きが必要な場合は明示的な指定（既存 `overwrite` 相当）を要求する。
4. 【新規】THE システム SHALL 同一入力に対して繰り返し実行しても副作用が増えない（冪等な）挙動とする。

### 要件 10: 構造化エラー出力と終了コード

**ユーザーストーリー:** エージェント利用者として、失敗時に機械可読なエラー情報と終了コードを受け取りつつ、人間が読む際には従来どおり日本語の分かりやすいメッセージを得たい。

#### 受け入れ基準

1. 【新規】WHEN 機械可読 JSON モードでエラーが発生した THEN システム SHALL エラー内容を構造化した JSON エラーオブジェクト（エラーコード / メッセージ等）として返す。
2. 【新規】THE システム SHALL 成功・失敗に応じた終了コード（成功=0、失敗=非 0）を返す。
3. 【既存】THE システム SHALL 人間向けのエラーメッセージを「現象・原因・対処方法」の構成で日本語出力する既存方針を維持する。
4. 【新規】THE システム SHALL 構造化エラー出力（JSON）と日本語メッセージ出力を両立させ、機械可読 JSON モードでは JSON を stdout に、日本語ログを stderr 等に振り分ける。
5. 【既存】IF 起点（ページ ID / Space キー）が存在しない、または権限がない THEN システム SHALL 現象・原因・対処方法を日本語で報告し、非 0 の終了コードで終了する。

### 要件 11: 後方互換と姉妹プロジェクトとの一貫性

**ユーザーストーリー:** 利用者として、従来どおり CLI を直接利用でき、姉妹プロジェクトと一貫した操作感を保ちたい。

#### 受け入れ基準

1. 【既存】WHEN 新モード/新フラグを指定しない THEN システム SHALL 既存 CLI（結合エクスポート / assess / fsexport / permexport）の挙動を変更しない。
2. 【既存】THE システム SHALL 既存の `--base-url` / `--proxy` / `--token` / `--output-dir` / `--config` / `--overwrite` / `--root-page-id` / `--space-key` 等の引数を踏襲する。
3. 【既存】THE システム SHALL 新設する引数名・振る舞いについて、姉妹プロジェクト（J2M-Export / G2M-Export）との一貫性を尊重する。
4. 【既存】THE システム SHALL 設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決する。
5. 【既存】THE システム SHALL Confluence のベース URL を末尾スラッシュ削除（rstrip）で正規化する既存方針を維持する。

### 要件 12: Skill 提供形態（ローカル Skill / 汎用 Agent Skills / MCP）

**ユーザーストーリー:** エージェント利用者として、GitHub Copilot と Kiro でローカル Skill を使えるようにしつつ、OSS として汎用 Agent Skills 形式や MCP サーバでも利用できるようにしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 最優先の提供形態として、ローカルに導入済みの Python と本リポジトリのチェックアウトを前提に CLI をサブプロセス起動するローカル Skill を提供する。
2. 【新規】THE ローカル Skill SHALL GitHub Copilot と Kiro の両ランタイムを対象とする。
3. 【新規】THE システム SHALL 汎用 Agent Skills 形式（`SKILL.md` + 補助スクリプト/指示書のディレクトリ構成）を提供する。
4. 【新規】WHERE 共有 PC への構成が容易に実現できる THE システム SHALL MCP サーバとして分析機能を公開する形態を（ローカル Skill より低い優先度で）提供する。
5. 【新規】THE Skill 定義 SHALL エージェントが本 spec の分析ユースケース (1)〜(6) を呼び出すための手順・入力・出力（機械可読 JSON）を記述する。
6. 【新規】THE Skill 定義 SHALL 前提環境（Python 3.8 以上の導入・リポジトリのチェックアウト・依存関係のインストール）を明記する。

### 要件 13: 認証情報の取り扱い（非機能要件）

**ユーザーストーリー:** 社内利用者として、認証トークンがプロセス一覧・コマンド履歴・ログ・出力に残らない安全な方式で分析を実行したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 認証トークンを環境変数経由で受け取れる手段を提供し、それを基本線とする（トークンを CLI 引数でそのまま渡すとプロセス一覧やシェル履歴に残るため）。
2. 【新規】THE Skill 定義 SHALL トークンを環境変数で渡す運用を推奨し、Skill 定義ファイル内にトークン値を直接記載しない。
3. 【新規】THE システム SHALL ログ出力（stdout / stderr を含む）に認証トークンを一切含めない。
4. 【新規】THE システム SHALL 機械可読 JSON 出力およびエラーオブジェクトに認証トークンを一切含めない。
5. 【既存】THE システム SHALL 既存の Bearer トークン認証・Proxy 方針（Proxy は環境変数 `HTTPS_PROXY` / `HTTP_PROXY` 対応）を踏襲する。

### 要件 14: 大規模ワークスペースへの対応とログ・ドキュメントの一貫性

**ユーザーストーリー:** 利用者として、大量のページ/添付を持つワークスペースでも分析が現実的な負荷で完了し、既存ツールと一貫した日本語ログ・ドキュメントで扱えるようにしたい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 子ページ・添付一覧の取得をページング処理で全件取得し、5xx / ネットワークエラーに指数バックオフでリトライする（既存方針を踏襲）。
2. 【既存】IF 個別ページの情報取得に失敗した THEN システム SHALL そのページをスキップし、分析を継続し、スキップ件数と ID を集計・報告する。
3. 【既存】THE システム SHALL 人間向けのログ出力・コメント・docstring を日本語（PEP 257 準拠）で記載する。
4. 【新規】WHERE 機械可読 JSON モード THE システム SHALL 日本語ログを stdout 以外へ振り分け、stdout の JSON と混在させない。
5. 【既存】WHEN 本機能を追加する THEN システム SHALL `README.md` および `README_DEV.md` を更新し、新しい設定キーのサンプルを `c2m_config_sample.yaml` に追加する。
6. 【新規】THE システム SHALL 新規追加する純粋ロジック（個別一覧抽出・圧縮カテゴリ集約・マクロ統計）を API 非依存の関数として実装し、単体テスト可能にする。

## スコープ外

本 spec は「エージェントからの状況把握・分析」と、そのための CLI 改善・Skill 整備に限定する。以下は対象外とする。

- **権限の自動適用をしない**: 検出・一覧化した個別権限を配置先（SharePoint / OneDrive 等）へ自動適用することは行わない（管理者の手作業または別ツールの責務）。
- **既存ツールの破壊的変更をしない**: 既存 CLI（結合エクスポート / assess / fsexport / permexport）の既存挙動・既存引数・既存出力フォーマットを壊す変更は行わない。新機能は追加として実装する。
- **実エクスポート出力をしない**: 本 spec の分析モードはファイルシステムへの実エクスポート・添付バイナリのダウンロード・差分同期/レジュームを行わない（既存 fsexport / sync の責務）。
- **マクロの自動修復をしない**: 手作業修復候補の「抽出・提示」までを対象とし、Markdown の自動修復は行わない。
- **Skill フォーマットは `SKILL.md` 標準に確定済み**: GitHub Copilot / Kiro / 汎用 Agent Skills は `SKILL.md` オープン標準に一本化し（配置先は上記「決定事項」参照）、MCP は公式 `mcp`（FastMCP）・stdio・optional 依存に確定した。本 spec では各ランタイムの将来的なフォーマット変更への追従（標準が変わった場合の再対応）は対象外とする。
- **Web UI（Streamlit）への露出**: 本 spec では必須としない（必要になれば後続で検討）。
