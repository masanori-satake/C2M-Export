# Requirements Document

## はじめに

本機能は、Confluence のページ階層を **樹形図（ページツリー）として可視化・出力する** 新しいモードを C2M-Export に追加するものである。各ノードにはタイトルとページ ID を基本とし、**付帯情報（個別アクセス制限の有無・使用マクロ名・添付数・最終更新日）を選択的に併記**できるようにする。出力は **テキスト / Markdown / JSON の 3 形式**に対応する。

既存の fsexport モード（spec `0004_filesystem_export`）はページ階層をディレクトリ/ファイルとして実体化する際に内部でツリーを構築する（`c2m_export/fs_export/tree.py`）。しかしその目的はローカルパス割り当て・重複回避であり、「人が読む／後続処理に渡すための階層ツリーそのものを、付帯情報付きで出力する」機能は存在しない。analyze モード（spec `0007_agent_analysis_skill`）は統計・集計を機械可読 JSON で返すものであり、親子関係を保持した階層ツリーは出力しない。

本 spec は、この不足（可視化目的の付帯情報付きページツリー出力）を埋める新モードを CLI として追加し、既存の `analyze` / `assess` / `fsexport` / `permexport` と同列の提供形態とする。あわせて、エージェント（GitHub Copilot / Kiro / 汎用 Agent Skills）から呼び出すための薄い Skill 定義（`confluence-tree`）を整備する。

本機能は既存 CLI の挙動を破壊せず、新たなモード/成果物として追加する。姉妹プロジェクト（J2M-Export / G2M-Export）との CLI 引数・振る舞いの一貫性、および将来の Confluence Cloud 対応を見据えた拡張性を維持する。

### 用語

- **ページツリー / 樹形図**: Confluence のページ親子関係を階層構造として表現したもの。ルートページを起点に子ページを再帰的に含む。
- **ノード**: ツリー上の 1 ページ。最小構成はタイトルと page_id。
- **付帯情報 (annotation)**: 各ノードに付加しうる補助データ。本 spec では「個別アクセス制限」「使用マクロ名」「添付数」「最終更新日」の 4 種を対象とする。
- **inline 併記**: ツリーの各ノード行に付帯情報を直接書き添える方式（例: タイトルの後ろに 🔒 マークや件数を付ける）。
- **別表 + リンク方式**: ツリー本体には軽量な情報（タイトル・ID・制限マーク程度）のみを載せ、詳細な付帯情報は別途テーブル（Markdown）または配列（JSON）として持ち、page_id で突き合わせる方式。
- **ハイブリッド方式**: text / markdown 形式では軽量な付帯情報を inline 併記し、詳細は別表で補い、json 形式では全付帯情報を各ノードに構造として格納する方式。本 spec が採用する方針。
- **選択制 (opt-in)**: 付帯情報の取得・表示を既定では行わず、利用者が明示指定したときのみ行う方式。
- **機械可読 JSON（stdout）**: ログや進捗表示を混ぜず、標準出力に単独で返す構造化 JSON。

### 既存機能で満たせる要件と新規実装が必要な要件の区別

既存 spec（`0007` / `0008`）の記法に合わせ、各受け入れ基準の冒頭に次の区分を明示する。

- **【既存】**: 既存コード（`ConfluenceClient` の各 API メソッド、`AnalysisConfig` の設定解決など）でほぼ満たせるもの。
- **【一部既存】**: 既存データ・API は揃っているが、集約・変換・描画ロジックの追加が必要なもの。
- **【新規】**: 現状コードに該当する収集・解析・出力が存在せず、新規実装が必要なもの。

### 既存コード資産（実装者向けの前提情報）

本機能の実装は、既存の `c2m_export/confluence.py` の `ConfluenceClient` を再利用する。以下は実在するメソッド（本 spec で利用を想定するもの）である。

- `get_space_root_pages(space_key, limit=25)`: スペースのルート（トップレベル）ページ一覧を全件取得（内部ページング）。
- `get_child_pages(page_id, limit=25)`: 指定ページの子ページ一覧を全件取得（内部ページング）。各要素は `id` / `title` を含む dict。
- `get_page(page_id, expand="body.storage,space")`: ページ本文（Storage Format）を含む詳細取得。マクロ解析に使用。
- `get_child_attachments(page_id, ...)`: 添付一覧の取得（添付数の算出に使用）。
- `get_restrictions(page_id)`: ページの個別コンテンツ制限（byOperation）取得。個別アクセス制限の判定に使用。
- `get_content_history(page_id, expand="lastUpdated,contributors")`: 最終更新日・更新者の取得。

設定は `AnalysisConfig`（`c2m_export/config.py`）相当の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決し、`base_url` / `token` / `proxy` / `space_keys` / `root_page_ids` を踏襲する。認証トークンは環境変数 `C2M_CONFLUENCE_TOKEN`（主）/ `CONFLUENCE_TOKEN`（互換）で受け取る。

マクロ名の集計方式は spec `0007` の確定事項を踏襲する（`body.storage` の structured-macro `ac:name` および legacy `conf-macro` の `data-macro-name` を集計）。

## 要件

### 要件 1: ページツリー出力モードの提供

**ユーザーストーリー:** 利用者として、Confluence のページ階層を樹形図として出力し、全体構造を一目で把握したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 指定された起点（Space キー / ルートページ ID）から子ページを再帰的にたどり、親子関係を保持したページツリーを構築する。
2. 【新規】THE システム SHALL 各ノードについて、最小構成としてページタイトルと page_id を含める。
3. 【新規】THE システム SHALL 既存 CLI（結合エクスポート / analyze / assess / fsexport / permexport）と同列の新モードとして、専用エントリーポイント `python -m c2m_export.tree` を提供する。
4. 【既存】THE システム SHALL 起点の指定に既存の `--space-key`（複数可）および `--root-page-id`（複数可）を踏襲する。
5. 【新規】IF 起点が指定されない（`--space-key` も `--root-page-id` も無い）THEN システム SHALL 現象・原因・対処方法を日本語で報告し、非 0 の終了コードで終了する。
6. 【新規】WHERE 複数の起点（複数スペース / 複数ルート）が指定される THE システム SHALL それぞれをツリーの最上位エントリとして順に出力する。

### 要件 2: 出力フォーマット（テキスト / Markdown / JSON）

**ユーザーストーリー:** 利用者として、用途に応じて樹形図をテキスト・Markdown・JSON のいずれかで受け取りたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 出力フォーマットを `text` / `markdown` / `json` から選択する手段（例: `--format`）を提供する。
2. 【新規】THE システム SHALL `text` 形式で、罫線（`├──` / `└──` / `│` 等）を用いた階層ツリーを出力する。
3. 【新規】THE システム SHALL `markdown` 形式で、ネストした箇条書き（インデント付きリスト）として階層ツリーを出力する。
4. 【新規】THE システム SHALL `json` 形式で、各ノードが子ノード配列を持つ再帰的な木構造を出力する。
5. 【新規】THE json 出力 SHALL キーが安定した構造とし、スキーマ識別子（`schema_version` 相当）を含める。
6. 【新規】THE システム SHALL 既定の出力フォーマットを定義する（設計で確定。候補は `text`）。
7. 【新規】WHERE `json` 形式が指定される THE システム SHALL ログ・進捗・装飾を含まない機械可読 JSON を stdout に単独で出力し、進捗・情報ログは stderr へ振り分ける。

### 要件 3: 付帯情報の選択的な取得（opt-in）

**ユーザーストーリー:** 利用者として、必要な付帯情報だけを選んでツリーに含め、不要な場合は軽量かつ高速にツリーだけを得たい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 付帯情報を既定では取得・表示せず、利用者が明示指定したときのみ取得する（opt-in）手段（例: `--include` に対象を列挙）を提供する。
2. 【新規】THE システム SHALL 選択可能な付帯情報として、少なくとも「個別アクセス制限（`restriction`）」「使用マクロ名（`macros`）」「添付数（`attachments`）」「最終更新日（`last_modified`）」の 4 種を定義する。
3. 【新規】WHEN 付帯情報が 1 つも指定されない THEN システム SHALL 付帯情報取得のための追加 API 呼び出しを行わず、タイトルと page_id のみのツリーを出力する。
4. 【新規】THE システム SHALL 付帯情報の取得がページごとに追加の API 呼び出しを伴うことを踏まえ、指定された種類のみを取得して不要な負荷を避ける。
5. 【新規】IF 特定ページの付帯情報取得に失敗した THEN システム SHALL そのページのツリー描画を中断せず、当該付帯情報を「取得失敗/不明」として扱い、取得失敗の件数を報告する。

### 要件 4: 付帯情報の表示方式（ハイブリッド）

**ユーザーストーリー:** 利用者として、付帯情報が増えてもツリーが読みにくくならず、かつ後続処理では全情報を機械可読に扱いたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL `text` / `markdown` 形式では、各ノード行に軽量な付帯情報を inline 併記する（例: 個別制限ありを示すマーク、添付数、マクロ種別数などの簡潔な表記）。
2. 【新規】WHERE inline 併記では情報量が過大になる付帯情報（例: 全マクロ名の列挙、制限対象ユーザー/グループの詳細）THE システム SHALL `markdown` 形式において、ツリー本体とは別のテーブルとして一覧し、page_id で突き合わせられるようにする（別表 + リンク方式）。
3. 【新規】THE システム SHALL `json` 形式では、各ノードに指定された全付帯情報を構造化フィールドとして格納する。
4. 【新規】THE システム SHALL inline 併記のマーク・記法を一貫した規則で定義し、ドキュメントに明記する（例: 🔒 = 個別アクセス制限あり）。
5. 【新規】THE システム SHALL 付帯情報が未指定のノード/形式では、対応フィールドを省略するか明示的に空/未取得と区別できる形で表現する。

### 要件 5: 付帯情報 (1) 個別アクセス制限マーク

**ユーザーストーリー:** 管理者として、ツリー上で個別アクセス制限が設定されたページを一目で見分けたい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL `get_restrictions(page_id)` を用いて各ページの個別コンテンツ制限の有無を判定する。
2. 【新規】THE システム SHALL 個別制限を持つノードに、`text` / `markdown` 形式で視認できるマーク（例: 🔒）を inline 併記する。
3. 【一部既存】THE システム SHALL `json` 形式および `markdown` の別表で、各制限ページについて Read / Read+Write の区別と、登場するユーザー/グループを提供する。
4. 【既存】IF 権限情報の取得に失敗した THEN システム SHALL ツリー描画を継続し、取得失敗の件数を報告する。
5. 【新規】THE システム SHALL 本付帯情報の取得可否（有効/無効）が opt-in 指定（要件 3）で制御されることを保証する。

### 要件 6: 付帯情報 (2) 使用マクロ名

**ユーザーストーリー:** 利用者として、各ページがどの Confluence マクロを使っているかをツリー上で把握し、移行時の修復対象を見積もりたい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL `get_page(page_id, expand="body.storage")` で取得した本文を解析し、structured-macro の `ac:name` および legacy `conf-macro` の `data-macro-name` を集計して、ページ単位の使用マクロ名（および回数）を得る（spec `0007` の集計方式を踏襲）。
2. 【新規】THE システム SHALL `text` / `markdown` 形式では、ノード行にマクロ種別数などの軽量表記を inline 併記し、全マクロ名の列挙は `markdown` の別表または `json` に委ねる。
3. 【新規】THE システム SHALL `json` 形式では、各ノードにマクロ名別の使用回数を構造として格納する。
4. 【新規】IF 本文の解析に失敗したページが存在する THEN システム SHALL そのページのマクロ情報を「解析失敗」として扱い、解析失敗の件数を報告してツリー描画を継続する。
5. 【新規】THE システム SHALL 本付帯情報の取得可否が opt-in 指定（要件 3）で制御されることを保証する。

### 要件 7: 付帯情報 (3) 添付数

**ユーザーストーリー:** 利用者として、各ページに添付が何件あるかをツリー上で把握したい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL `get_child_attachments(page_id)` を用いて各ページの添付件数を取得する。
2. 【新規】THE システム SHALL `text` / `markdown` 形式では、添付がある場合にノード行へ添付件数を inline 併記する。
3. 【新規】THE システム SHALL `json` 形式では、各ノードに添付件数を数値フィールドとして格納する。
4. 【新規】THE システム SHALL 本付帯情報の取得可否が opt-in 指定（要件 3）で制御されることを保証する。
5. 【新規】IF 添付一覧の取得に失敗した THEN システム SHALL その件数を「不明」として扱い、取得失敗の件数を報告してツリー描画を継続する。

### 要件 8: 付帯情報 (4) 最終更新日

**ユーザーストーリー:** 利用者として、各ページの最終更新日をツリー上で把握し、古い枝を見分けたい。

#### 受け入れ基準

1. 【一部既存】THE システム SHALL `get_content_history(page_id, expand="lastUpdated")`（または `get_page` の version 情報）を用いて各ページの最終更新日を取得する。
2. 【新規】THE システム SHALL `text` / `markdown` 形式では、ノード行に最終更新日を inline 併記する。
3. 【新規】THE システム SHALL `json` 形式では、各ノードに最終更新日（ISO 8601 形式）を格納する。
4. 【新規】IF 最終更新日が取得できない THEN システム SHALL そのノードを「不明」として区別し、取得失敗の件数を報告してツリー描画を継続する。
5. 【新規】THE システム SHALL 本付帯情報の取得可否が opt-in 指定（要件 3）で制御されることを保証する。

### 要件 9: 非対話・非破壊・冪等な実行

**ユーザーストーリー:** 利用者/エージェントとして、対話で止まらず、Confluence やローカルに破壊的変更を与えない安全な実行をしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 本モード実行時に、標準入力を要求する対話プロンプトを一切出さない。
2. 【新規】WHEN 本モードが実行される THEN システム SHALL Confluence への書き込みおよび添付バイナリのダウンロードを行わない（読み取り専用）。
3. 【新規】THE システム SHALL 既定では標準出力へ結果を出し、ファイルへ書き出す場合でも既定で無確認上書きを行わず、上書きには明示指定（既存 `--overwrite` 相当）を要求する。
4. 【新規】THE システム SHALL 同一入力に対して繰り返し実行しても副作用が増えない（冪等な）挙動とする。

### 要件 10: 構造化エラー出力と終了コード

**ユーザーストーリー:** エージェント利用者として、失敗時に機械可読なエラー情報と終了コードを受け取りつつ、人間向けには日本語の分かりやすいメッセージを得たい。

#### 受け入れ基準

1. 【新規】WHEN `json` 形式でエラーが発生した THEN システム SHALL エラー内容を構造化した JSON エラーオブジェクト（エラーコード / メッセージ等）として返す。
2. 【新規】THE システム SHALL 成功・失敗に応じた終了コード（成功=0、失敗=非 0）を返す。
3. 【既存】THE システム SHALL 人間向けのエラーメッセージを「現象・原因・対処方法」の構成で日本語出力する既存方針を維持する。
4. 【新規】WHERE `json` 形式 THE システム SHALL JSON を stdout に、日本語ログ・エラー詳細を stderr に振り分け、混在させない。
5. 【既存】IF 起点が存在しない、または権限がない THEN システム SHALL 現象・原因・対処方法を日本語で報告し、非 0 の終了コードで終了する。

### 要件 11: 後方互換と姉妹プロジェクトとの一貫性

**ユーザーストーリー:** 利用者として、既存 CLI の挙動を損なわず、姉妹プロジェクトと一貫した操作感を保ちたい。

#### 受け入れ基準

1. 【既存】WHEN 本モードを使わない THEN システム SHALL 既存 CLI（結合エクスポート / analyze / assess / fsexport / permexport）の挙動を変更しない。
2. 【既存】THE システム SHALL 既存の `--base-url` / `--proxy` / `--token` / `--config` / `--root-page-id` / `--space-key` / `--overwrite` 等の引数を踏襲する。
3. 【既存】THE システム SHALL 設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決する。
4. 【既存】THE システム SHALL Confluence のベース URL を末尾スラッシュ削除（rstrip）で正規化する既存方針を維持する。
5. 【新規】THE システム SHALL 新設する引数名・振る舞いについて、既存モードおよび姉妹プロジェクト（J2M-Export / G2M-Export）との一貫性を尊重する。

### 要件 12: Skill 提供形態（confluence-tree）

**ユーザーストーリー:** エージェント利用者として、GitHub Copilot / Kiro / 汎用 Agent Skills からページツリー出力を呼び出したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 本モードを呼び出す Skill `confluence-tree` を、正本 `skills/confluence-tree/` に `SKILL.md` + 補助スクリプトとして定義する。
2. 【新規】THE システム SHALL 正本を `.kiro/skills/confluence-tree/` および `.github/skills/confluence-tree/` へ複製配置する（正本からの上書きコピーを厳守。既存スキルと同じ同期ルール）。
3. 【新規】THE SKILL.md SHALL 前提環境（Python 3.8 以上・リポジトリのチェックアウト・依存インストール）、入力（起点・フォーマット・付帯情報の選択）、出力（text / markdown / json）を記述する。
4. 【新規】THE Skill 定義 SHALL トークンを環境変数で渡す運用を推奨し、Skill 定義ファイル内にトークン値を直接記載しない。
5. 【新規】THE SKILL.md 正本 SHALL 先頭に「正本と複製先、同期ルール」を示すコメントを含める（既存 `confluence-analysis` / `confluence-setup` と同形式）。

### 要件 13: 認証情報の取り扱い（非機能要件）

**ユーザーストーリー:** 社内利用者として、認証トークンがプロセス一覧・履歴・ログ・出力に残らない方式で実行したい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 認証トークンを環境変数（`C2M_CONFLUENCE_TOKEN` 主 / `CONFLUENCE_TOKEN` 互換）で受け取れる手段を提供し、それを基本線とする。
2. 【新規】THE システム SHALL ログ出力（stdout / stderr を含む）・ツリー出力・エラーオブジェクトに認証トークンを一切含めない。
3. 【既存】THE システム SHALL 既存の Bearer トークン認証・Proxy 方針（環境変数 `HTTPS_PROXY` / `HTTP_PROXY` 対応、環境変数が YAML の `proxy` を上書きする既存挙動）を踏襲する。

### 要件 14: 大規模ワークスペースへの対応とドキュメント・テストの一貫性

**ユーザーストーリー:** 利用者として、大量ページを持つスペースでも現実的な負荷でツリーを得られ、既存ツールと一貫した日本語ログ・ドキュメントで扱いたい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 子ページ・添付一覧の取得をページング処理で全件取得し、5xx / ネットワークエラーに指数バックオフでリトライする（既存 `ConfluenceClient` 方針を踏襲）。
2. 【既存】IF 個別ページの取得に失敗した THEN システム SHALL そのページをスキップまたは「不明」として扱い、ツリー描画を継続し、スキップ/失敗件数と ID を集計・報告する。
3. 【既存】THE システム SHALL 人間向けのログ出力・コメント・docstring を日本語（PEP 257 準拠）で記載する。
4. 【新規】THE システム SHALL ツリー構築・付帯情報の集約・各フォーマットへの描画を、API 非依存の純粋ロジックとして実装し、単体テスト可能にする（API 呼び出し層と描画層を分離）。
5. 【既存】WHEN 本機能を追加する THEN システム SHALL `README.md` および `README_DEV.md` を更新し、新しい設定キーのサンプルを `c2m_config_sample.yaml` に追加する。
6. 【新規】THE システム SHALL 付帯情報取得が opt-in のときのみ追加 API を呼ぶ設計とし、付帯情報なしのツリー出力が子ページ一覧取得のみで完了することを保証する。

## スコープ外

- **ページ内容のエクスポートをしない**: 本モードは階層ツリーと付帯情報の出力に限定し、本文の Markdown 変換・添付バイナリのダウンロード・差分同期は行わない（既存 fsexport / sync の責務）。
- **統計集計の重複実装をしない**: 移設リスク・鮮度分布などの集計は既存 analyze / assess の責務であり、本 spec では再実装しない。付帯情報はあくまでノード単位の併記にとどめる。
- **マクロの自動修復をしない**: 使用マクロ名の「表示」までを対象とし、修復候補の分類や自動修復は行わない（分類は analyze の責務）。
- **権限の自動適用をしない**: 個別制限の「表示」までを対象とし、配置先への権限適用は行わない。
- **Web UI（Streamlit）への露出**: 本 spec では必須としない（必要になれば後続で検討）。
- **付帯情報の 4 種を超える拡張**: 本 spec では「個別アクセス制限 / 使用マクロ名 / 添付数 / 最終更新日」の 4 種を対象とする。ラベル・更新者・本文バイト数等の追加は拡張容易な設計とするが、本 spec のスコープ外とする。
