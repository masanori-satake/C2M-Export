# Requirements Document

## はじめに

本機能は、分析モードの**非同期ジョブプロトコル**（応答性改善フェーズ 3、spec 0011 / 0012 の後続）である。エージェントのターミナル実行はブロッキングであり、同期実行ではプロセスが終わるまで結果も進捗も返らない。フェーズ 1 のハートビートと上限、フェーズ 2 の事前見積もりで「待てる」状態にはなったが、10 分超の実行では依然として1回の呼び出しが長時間を占有する。

本フェーズでは、実行をジョブとして分離する:

- `--detach` で開始すると、ワーカーを別プロセスで起動して即座に `job_id` を返す（start）。
- ワーカーは進捗を `progress.json` に原子的に書き続ける（書いて rename）。進捗源はフェーズ 1 のハートビート（フェーズ・経過・収集済み件数）と、開始時に行うフェーズ 2 の見積もり（推定総ページ数）。
- `--job-status <job_id>` はファイルを読み、小さい JSON を即座に返す（status）。
- `--job-result <job_id>` は完了時に、結果ファイルへのパスと要約のみを返す（result）。結果の全量はファイルにあり、エージェントのコンテキストに detail 全量を入れない。
- `--job-cancel <job_id>` はキャンセルフラグを置き、ワーカーが協調的に中断する（収集済み分はチェックポイントに残り、`--resume` で再開できる）。

設計判断:

- ジョブの保存先は既定 `.c2m_analyze_jobs/`（`--job-dir` で変更可）。ジョブ記録にトークンや引数列は保存しない（スコープの要約のみ）。ワーカーへの引き継ぎはプロセス引数で行い、ファイルには残さない。
- ワーカーの切り離しは OS 標準の方法（POSIX: 新規セッション / Windows: DETACHED_PROCESS）で行い、追加依存は入れない。
- ワーカーが異常終了して進捗ファイルが止まった場合は、status が「更新が古い（stale）」ことを明示する。PID の生存確認は OS 差が大きいため行わない。
- MCP の3ツール化（analyze_start / status / result）は本フェーズの対象外とする。MCP サーバはセッション常駐プロセスであり、長時間ジョブの寿命管理モデルが CLI と異なるため、ファイルベースのジョブ基盤を先に安定させ、MCP は同じジョブストアを参照する形で別途検討する（同期版ツールは互換のため現状維持）。

人間向け CLI の同期実行と「stdout は純粋な JSON」という既存契約、JSON スキーマ（schema_version 1.2）は変更しない。ジョブ操作コマンドの出力はジョブ用の小さい JSON とする。

## 要件

### 要件 1: ジョブ開始（start）

**ユーザーストーリー:** スキル利用者として、長い分析を開始したら即座に応答が返り、他の作業を続けたい。

#### 受け入れ基準

1. THE CLI SHALL `--detach` 指定時にワーカーを別プロセスで起動し、`job_id` を含む JSON を即座に返して終了する。
2. THE システム SHALL ジョブ記録（ジョブ ID・開始時刻・PID・スコープ要約）をジョブディレクトリに保存する。トークンおよび引数列は保存しない。
3. THE ワーカー SHALL 開始時に事前見積もり（spec 0012）を行い、推定総ページ数を進捗に含めるよう試みる。見積もりに失敗しても本実行は継続する。

### 要件 2: 進捗（progress / status）

#### 受け入れ基準

1. THE ワーカー SHALL 進捗（状態・フェーズ・経過秒数・収集済み件数・推定総ページ数・最終更新時刻）を `progress.json` へ原子的に（書いて rename）周期的に書く。
2. THE CLI SHALL `--job-status <job_id>` で進捗 JSON を即座に返す。ジョブが存在しない場合はその旨を明示する。
3. THE status SHALL 実行中ジョブの進捗更新が古い場合に、その旨（stale）を明示する。
4. THE システム SHALL ジョブ ID を検証し、パストラバーサル等に悪用できない形にする。

### 要件 3: 結果取得（result）

#### 受け入れ基準

1. THE ワーカー SHALL 完了時に結果 JSON 全量を結果ファイルへ書き、進捗を最終状態（done / partial / error）にする。
2. THE CLI SHALL `--job-result <job_id>` で、結果ファイルへのパスと要約（状態・収集件数・uncertainties の要点・エラー情報）のみを返す。未完了の場合は現在の状態を返し、その旨を明示する。

### 要件 4: 中断（cancel）

#### 受け入れ基準

1. THE CLI SHALL `--job-cancel <job_id>` でキャンセルフラグを置き、ワーカーが協調的中断で停止する（結果は partial として残る）。

### 要件 5: スキル手順と互換性

#### 受け入れ基準

1. THE スキル（SKILL.md）SHALL 大きい対象では非同期開始を選び、30〜60 秒間隔で status を確認して経過を利用者へ伝え、完了後に result の要約だけを読む手順を案内する。
2. THE 補助スクリプト SHALL `--detach` をそのまま子プロセスへ渡し、ジョブ操作コマンド（status / result / cancel）には既定 timeout を補わない。
3. THE 同期実行 SHALL 従来どおり動作し、出力形式も変わらない。
