# 信頼性レビュー所見（spec 0019）

実施日: 2026-11-06。区分は「確認済み（問題なし）」「問題あり（本 PR で修正）」「観察（修正せず、必要なら別途提案）」の3つ。

## V1 非同期ジョブ

- 確認済み: ジョブ ID の形式検証（パストラバーサル防止）、進捗・結果の原子書き込み、stale 判定（進捗はハートビート連動で5秒ごとに更新され、90秒無更新で stale を立てる。閾値に意味がある）、cancel の協調中断、結果は要約のみ返却、job.json にトークン・引数列を保存しない、結果ファイルはトークンで sanitize 済み。
- **問題あり F1**: `request_cancel` の存在判定が job.json のみに依存し、`build_status`（job.json または progress.json で存在扱い）と不整合。ワーカー起動直後（Popen からジョブ記録作成までの間）や job.json が読めない状態では、status で見えるジョブを cancel できない（not_found、終了コード4になる）。→ 存在判定を build_status と揃える。
- 観察 O1: worker.log にはワーカーの stdout として結果 JSON 全量が複製される（sanitize 済みのため秘密情報の問題はない。ディスク重複のみ）。
- 観察 O2: 古いジョブ記録の自動掃除はない。result.json は detail 全量を含みうるため、長期間使うと蓄積する。ただし自動削除は利用者の結果ファイル参照と競合しうるため、本 PR では入れず、別途提案とする。
- 観察: `--token` を引数で渡して detach した場合、ワーカーの引数列にもトークンが載る（プロセス一覧から見える）。直接実行と同じ既知の制約で、スキルは環境変数経由を推奨済み。許容する。

## V2 チェックポイント再開

- 確認済み: スコープハッシュに対象（base_url、起点、Space、all_spaces、CQL）と収集系フラグ（collect_macros を含む全 collect_* と analyze_restrictions）が含まれ、チェックポイントファイル自体がハッシュ名で分離される。条件を変えて再開しても別ファイルになるため、誤って前回の収集分が混ざることはない。表示系オプション（limit / sort / mode）と集計系パラメータ（stale-days 等）は収集結果に影響しないため、含まれないのが正しい。
- 確認済み: 破損行はスキップして件数を数え、結果の uncertainties に出す。同一ページの重複行は page_id で一意化される。成功時はチェックポイントファイルが削除され、古い再開が残らない。
- 観察 O4: 同一スコープの同時実行はチェックポイント追記が競合しうるが、破損行として許容・集計される設計であり、同時実行自体が想定運用ではない。許容する。

## V3 先読みフォールバック

- 確認済み: 子孫取得は上限超過・中断時に部分結果を返さず例外化され（`get_descendants` が RuntimeError）、呼び出し側は起点単位で個別取得にフォールバックする。ちょうど上限件数で打ち切られた不完全な一覧が「完全」と扱われる経路はない。親を特定できない要素が1つでもあれば起点の先読み全体を無効化する。DFS 側は visited 集合で循環・重複を吸収する。

## V4 並列収集

- 確認済み: 全体把握の並列結果は入力順に組み立てられ、出力の内容・順序は直列と同一。ワーカー関数 `_collect_space_overview_one` は共有状態（raw_inventory）を変更しない。中断は待機中も0.5秒間隔で判定され、executor は wait=False で閉じる（実行中タスクの結果は破棄される）。セッションはスレッドローカルで、ワーカースレッドごとに独立する。

## V5 見積もり

- 確認済み: 起点ごとの子孫数取得に失敗した場合は起点のみとして数え、失敗した起点 ID と「過小評価の可能性」の注記を返す。対象0件でも固定リクエスト分で推定を返す。レイテンシ実測ができない場合はフォールバック値（0.3秒）を使う。is_large は上限で丸めていない対象ページ数で判定する。
- **問題あり F2**: `--all-spaces` の見積もりで Space 一覧の取得が認証失敗（401/403）でも、`ApiError` として包まれて終了コード 5（API_ERROR）になる。本実行経路では同じ失敗が AUTH_FAILED（終了コード3）になる。errors.md の「認証失敗は繰り返さない」というエージェントの判断が誤分類で崩れるため、認証失敗はそのまま AuthFailedError として伝播させる。

## V6 テストの質

- 確認済み: 全518件を3回連続実行し、すべて通過（フレークなし、各回約7秒）。
- 確認済み: stale 判定、cancel、子孫数取得失敗、チェックポイントの追記・再開スキップ・スコープ一致判定、並列と直列の等価性はテストで固定されている。
- 観察 O3: detach からワーカー起動・結果取得までを実プロセスで通す E2E テストはない（Popen はモック、ワーカーモードはプロセス内で検証）。部品の組み合わせとしては妥当なカバーだが、実機スモークテスト（Windows + Copilot で見積もり→実行→報告を通す確認）で補完するのがよい。

## V7 秘密情報

- 確認済み: トークンはセッションの Authorization ヘッダーにのみ保持され、ログ出力箇所にヘッダーやトークンを出すコードはない。標準出力・標準エラーの最終出力、ジョブの結果ファイルはいずれも sanitize を通る。チェックポイントとジョブ記録に資格情報は含まれない。
