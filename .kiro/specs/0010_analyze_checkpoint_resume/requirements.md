# Requirements Document

## はじめに

本機能は、分析モード（`python -m c2m_export.analyze` / assessment 収集層）に対して、**チェックポイントによる中間永続化**・**中断からの再開（レジューム）**・**部分成功結果の確実な出力（partial）**を追加するものである。

実運用で、ワークスペースレベル（スペース全体）の分析を行うと、収集対象が数千〜1 万ページ規模に達することがある。現状の分析モードは、収集層（`Collector.collect()`）が全ページのメタデータをメモリ上に収集し終えてから分析（`analyze_inventory()`）し、最後に JSON を一括出力する「収集完了まで成果物がゼロ」の構造である。このため、長時間（数十分〜1 時間超）走らせた末に、ネットワーク断・プロセス kill・タイムアウトで中断すると、それまでの収集結果がすべて失われ、時間が無駄になる。

本機能は、この最悪ケース（長時間かけて最後にゼロ）を解消する。具体的には、(1) 収集済みの生メタデータを一定間隔で永続ファイル（チェックポイント）へ追記して失われないようにし、(2) 再実行時に同一スコープのチェックポイントがあればそこから再開し、(3) 中断・エラー時にも、そこまでに収集できた範囲で集計した JSON を `status: "partial"` として確実に出力する。

本機能は 0007（分析 Skill・共通 1 層 `run_analysis` → `AnalysisResponse`）および 0008（収集層拡張）が確立した枠組みを**破壊せず、追加のみ・後方互換**で実装する。既存の分析エンジン・JSON スキーマ・Skill/MCP の枠組みは作り直さない。チェックポイントは分析モードの収集層に閉じた機構であり、fsexport のマニフェスト（0004/0005）とは別物として扱う（fsexport は既にレジューム・差分同期を実装済みのため本 spec の対象外）。

### スコープの位置づけ

ワークスペース全体のような大規模ジョブの「中断耐性」を主題とするが、本 spec は**分析モードに限定**する。理由は、分析モードの成果物（集計 JSON）は収集済み中間データから後でまとめ直せる性質があり、収集と出力を分離してチェックポイント化しやすいためである。以下は本 spec の対象外とする。

- **結合エクスポートモード（`cli.py`）の中断耐性**: 成果物が 1 本の Markdown へのストリーム追記であり、中断時の扱いが分析と異なるため、別 spec で扱う。ただし本 spec の永続化基盤は将来 結合モードへ流用できるよう設計で配慮する。
- **fsexport のレジューム・差分同期**: 0004/0005 で実装済み。本 spec では扱わない。
- **収集のストリーミング化による根本的なメモリ枯渇対策**: `Collector.collect()` をジェネレータ化し、全件をメモリに保持せず 2 パスで集計する本格対応は大規模改修となるため、将来 spec とする（本 spec はチェックポイント永続化・レジューム・partial 出力・シグナル対応までに絞る）。

### 用語

- **分析モード**: `python -m c2m_export.analyze`（共通 1 層 `analysis/api.py:run_analysis`）および、その収集を担う assessment 収集層（`assessment/collector.py` の `Collector`）を指す。
- **チェックポイント**: 収集フェーズで得た生メタデータ（`RawInventory` 相当：ページメタ・添付メタ・制限・来歴・ラベル等）を、収集の進行に伴い永続化する中間ファイル。本 spec では JSONL（1 行 1 レコードの追記型）とする。
- **スコープ**: 1 回の分析が対象とする範囲を一意に識別する情報の組。少なくとも `base_url`・起点（`space_keys` / `root_page_ids` / `all_spaces` / `cql`）・収集オプション（2 段収集のオン/オフ、`--deep` 系フラグ、`stale` 等の判定閾値のうち収集結果に影響するもの）から構成する。
- **スコープハッシュ**: スコープを正規化して算出する識別子。チェックポイントファイル名に用い、別スコープのチェックポイントとの取り違えを防ぐ。
- **レジューム**: 中断された分析を、チェックポイントに記録済みの収集結果を再利用し、未収集分から再開すること。
- **部分成功結果（partial）**: 収集が全件完了しなかった場合に、そこまでに収集できた範囲で集計して出力する分析結果。`status: "partial"` で示す。
- **flush 粒度**: チェックポイントへ追記・同期（fsync 相当）する間隔（1 件ごと、または N 件ごと）。

### 前提と仮定（曖昧性に対する明示的な仮定）

- 本 spec は 0007・0008 が完了していることを前提とし、その上に**追加のみ**で積む。分析純粋関数・JSON スキーマ骨格・Skill/MCP 枠組みは再利用する。
- チェックポイントは収集層（I/O 層）に閉じた機構とし、分析純粋関数（API 非依存）はチェックポイントの有無に依存しない。
- チェックポイントの保存先は、既定で作業ディレクトリ配下の `.c2m_analyze_checkpoint/` とし、ファイル名にスコープハッシュを用いる（場所・構造の最終確定は設計フェーズ）。
- 収集対象ページの収集順は、同一スコープ・同一 Confluence 状態であれば実行間で安定していることを前提に再開位置を判定する。収集順が揺れうる場合の整合は、page_id を不変キーとした「収集済み集合」の照合で吸収する（詳細は設計で確定）。
- `schema_version` の運用は 0007/0008 の確定事項（キー追加＝後方互換なマイナー更新、削除・リネーム・意味変更＝メジャー）に従う。本 spec の JSON 追加（`status: "partial"`・収集進捗情報等）はマイナー更新に収める。
- 設定解決は既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）を踏襲する。

### 既存機能で満たせる要件と新規実装が必要な要件の区別

0007/0008 と同様、各受け入れ基準の冒頭に区分を明示する。

- **【既存】**: 0007/0008 または既存コードでほぼ満たせるもの。
- **【一部既存】**: 既存の骨格・契約は利用できるが、新規メソッド追加・フィールド追加・ロジック追加が必要なもの。
- **【新規】**: 現状に該当する機構が存在せず、新規実装が必要なもの。

## 要件

### 要件 1: 収集済みメタデータのチェックポイント永続化

**ユーザーストーリー:** 利用者として、大規模な分析の収集途中でプロセスが中断しても、それまでに収集できたページ/添付のメタデータが失われないようにしたい。長時間かけて最後にゼロ、という事態を避けたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 収集フェーズで得た生メタデータ（ページメタ・添付メタ・個別制限・および 0008 で収集する来歴/ラベル/コメント/実効制限等のうち収集済みのもの）を、収集の進行に伴いチェックポイントファイルへ永続化する。
2. 【新規】THE チェックポイント SHALL JSONL 形式（1 行 1 レコードの追記型）とし、1 レコードが収集単位（ページ 1 件相当）を表す。
3. 【新規】THE システム SHALL チェックポイントへの追記を、プロセスが途中中断しても追記済みレコードが失われにくい方法（逐次 flush、追記モード書き込み）で行う。
4. 【新規】THE システム SHALL チェックポイントの flush 粒度（1 件ごと / N 件ごと）を設定で制御できるようにし、既定値を定める（既定値は設計で確定）。
5. 【新規】THE チェックポイント SHALL 自身が対象とするスコープ（`base_url`・起点・収集オプション）を識別できる情報を保持し、別スコープのチェックポイントと取り違えないようにする（ヘッダレコードまたはファイル名のスコープハッシュ、方式は設計で確定）。
6. 【一部既存】THE システム SHALL チェックポイント永続化を収集層（`Collector`）に組み込み、分析純粋関数・JSON スキーマ・Skill/MCP の枠組みを変更しない（追加のみ）。

### 要件 2: 中断からの再開（レジューム）

**ユーザーストーリー:** 利用者として、中断した分析を再実行したとき、既に収集済みのページを再取得せず、未収集分から再開したい。

#### 受け入れ基準

1. 【新規】WHEN レジュームが指定され、今回のスコープと一致するチェックポイントが存在する THEN システム SHALL チェックポイントの収集済みレコードを読み込み、未収集のページ/添付のみを収集して分析を完了する。
2. 【新規】THE システム SHALL 収集済み判定に page_id（不変キー）を用い、チェックポイントに記録済みのページを再取得しない。
3. 【新規】WHEN レジューム指定時にチェックポイントのスコープが今回の実行指定と一致しない THEN システム SHALL そのチェックポイントを再開に使わず、現象・原因・対処方法（別スコープである旨、チェックポイントを破棄して新規実行する等）を日本語で報告し、安全側（既存チェックポイントを誤って上書き・混用しない）で扱う。
4. 【新規】IF チェックポイントが破損・一部不正なレコードを含む THEN システム SHALL 読み取り可能なレコードまでを収集済みとして復元し、不正レコードを `uncertainties` に記録して継続する（破損で全体を停止させない）。
5. 【新規】THE システム SHALL レジューム実行時に、復元（再利用）件数・新規収集件数をログおよび JSON の収集進捗情報に記録する。
6. 【新規】WHERE レジュームが指定されない THE システム SHALL チェックポイントが存在しても再開に使わず、新規に収集を開始する（既定の非レジューム実行では過去のチェックポイントを参照しない。ただし要件 1 の永続化は行う）。

### 要件 3: 部分成功結果（partial）の確実な出力

**ユーザーストーリー:** 利用者として、収集が全件完了しなくても、そこまでに集まった範囲で分析結果を得たい。長時間の実行が完全な無駄にならないようにしたい。

#### 受け入れ基準

1. 【新規】WHEN 収集が全件完了する前に中断（シグナル・回復不能なエラー・タイムアウト）が発生する THEN システム SHALL そこまでに収集できた範囲で分析（集計）を実行し、結果 JSON を出力する。
2. 【新規】THE 部分成功結果 SHALL `status: "partial"`（0007 の `ok` / `error` と区別できる値）で示し、全件完了時のみ `status: "ok"` とする。
3. 【一部既存】THE システム SHALL 部分成功結果の `uncertainties` に、収集済み件数・未収集（打ち切り）の事実・打ち切り理由（中断種別）を機械可読に記録する。
4. 【新規】THE システム SHALL 部分成功結果にも、収集できた範囲の各ユースケース集計（`stale` / `restricted` / `macros` 等）を可能な限り出力し、集計が収集途中の母数に基づく旨を明示する。
5. 【新規】THE システム SHALL 部分成功か全件完了かにかかわらず、出力 JSON を stdout に単独で出力し、日本語ログは stderr に分離する 0007 の規約を踏襲する。

### 要件 4: 中断シグナルの捕捉と安全な終了

**ユーザーストーリー:** 利用者として、Ctrl+C やタイムアウトによる kill でプロセスが止められても、収集済み分を活かした結果が残ってほしい。

#### 受け入れ基準

1. 【新規】THE システム SHALL SIGINT（Ctrl+C）および SIGTERM を捕捉し、捕捉時にチェックポイントを確定（flush）してから、要件 3 の部分成功結果を出力して終了する。
2. 【新規】THE システム SHALL シグナル捕捉時の終了を、収集データの破損やチェックポイントの不整合を生じさせない方法で行う。
3. 【新規】THE システム SHALL シグナルによる中断を、通常の回復不能エラーと区別して `uncertainties`（打ち切り理由）に記録する。
4. 【新規】WHERE シグナル捕捉後の部分出力処理自体が失敗する THE システム SHALL 最低限チェックポイントが保全されている状態で終了し、次回レジュームで収集済み分を回収できるようにする。

### 要件 5: チェックポイントのスコープ整合と保存場所

**ユーザーストーリー:** 利用者として、複数スペースや複数サーバを分析するとき、チェックポイントが取り違えられて誤った再開や混合が起きないようにしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL チェックポイントの既定保存場所を作業ディレクトリ配下の `.c2m_analyze_checkpoint/` とし、ファイル名にスコープハッシュを含める（例: `<scope-hash>.jsonl`）。
2. 【新規】THE システム SHALL スコープハッシュを `base_url`・起点（`space_keys` / `root_page_ids` / `all_spaces` / `cql`）・収集結果に影響する収集オプションから正規化して算出し、同一スコープで安定・異なるスコープで衝突しにくいものとする。
3. 【新規】THE システム SHALL チェックポイント保存場所を設定（CLI 引数 / YAML）で変更できるようにする。
4. 【新規】THE システム SHALL チェックポイントディレクトリが存在しない場合に作成し、作成・書き込みに失敗した場合は現象・原因・対処方法を日本語で報告する。
5. 【新規】WHERE 分析が全件正常完了した THE システム SHALL 既定でチェックポイントを後始末（削除またはチェックポイントに完了印を付与）できるようにし、その挙動を設定で制御できるようにする（既定挙動は設計で確定）。

### 要件 6: 既定挙動・オプトアウトと CLI/設定

**ユーザーストーリー:** 利用者として、特別な指定をしなくても中断耐性の恩恵を受けたい。一方で、チェックポイントを作りたくない場合は無効化したい。

#### 受け入れ基準

1. 【新規】THE システム SHALL チェックポイント永続化を**既定で有効（ON）**とし、何も指定しなくても収集中の永続化と中断時の partial 出力が働くようにする。
2. 【新規】THE システム SHALL チェックポイント永続化を無効化する手段（例: `--no-checkpoint`）を提供する。
3. 【新規】THE システム SHALL レジュームを明示的に有効化する手段（例: `--resume`）を提供し、既定（レジューム未指定）では過去チェックポイントから再開しない。
4. 【新規】THE システム SHALL flush 粒度（例: `--checkpoint-interval`）とチェックポイント保存場所（例: `--checkpoint-dir`）を CLI/設定で指定できるようにする。
5. 【一部既存】THE システム SHALL 本機能の設定を既存の 0007/0008 の `AnalysisConfig` / `AnalysisParams` に**追加のみ**で拡張し、新設の独立 Config を作らない。
6. 【既存】THE システム SHALL 設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決する。

### 要件 7: 大規模・部分成功の報告とログ

**ユーザーストーリー:** 利用者として、収集の進捗と、どこまで収集できたか・何を再利用したかを把握したい。

#### 受け入れ基準

1. 【既存】THE システム SHALL 収集の進捗（処理件数）を日本語ログで定期的に報告する（既存の進捗ログを踏襲する）。
2. 【新規】THE システム SHALL チェックポイント確定件数・レジューム時の再利用件数・新規収集件数を日本語ログに記録する。
3. 【新規】THE システム SHALL 中断時に、部分成功結果を出力した旨と、次回レジューム方法（`--resume` 指定）を日本語で案内する。
4. 【既存】THE システム SHALL エラーメッセージを「現象・原因・対処方法」の構成で出力する。
5. 【既存】WHERE 機械可読 JSON モード THE システム SHALL JSON を stdout、日本語ログを stderr に分離する。

### 要件 8: 後方互換と安全性（非機能）

**ユーザーストーリー:** 既存利用者・既存エージェントとして、本機能が追加されても既存の分析 JSON 出力・Skill/MCP が壊れないようにしたい。

#### 受け入れ基準

1. 【新規】THE システム SHALL 本機能の JSON 追加（`status: "partial"`・収集進捗情報・新 `uncertainties` キー）を**追加のみ・後方互換**で行い、既存キーの型・名称・意味を変更しない。
2. 【既存】THE システム SHALL キー追加・`status` 値の追加を `schema_version` のマイナー更新として扱い、削除・リネーム・意味変更を本 spec では行わない。
3. 【既存】THE システム SHALL 認証トークンをチェックポイント・ログ・JSON 出力・エラーオブジェクトに一切含めない（0007 の多層サニタイズをチェックポイント経路にも適用する）。
4. 【新規】THE チェックポイントファイル SHALL 秘匿情報（トークン等）を含まず、収集済みメタデータと最小限のスコープ識別情報のみを保持する。
5. 【既存】WHEN 本機能を追加する THEN システム SHALL `README.md` / `README_DEV.md` / `c2m_config_sample.yaml` / Skill 定本（`skills/confluence-analysis/SKILL.md`）と複製（`.github/skills/` / `.kiro/skills/`）・MCP サーバ記述・`.kiro/steering/*.md` を新オプション・新 `status`・新キーに合わせて更新する。
6. 【新規】THE システム SHALL チェックポイント・レジューム・partial 出力のロジックを、可能な範囲で API 非依存の純粋関数（スコープハッシュ算出・収集済み集合の差分判定・JSONL の読み書き）として実装し、API モック不要で単体テスト可能にする。

## スコープ外

本 spec は「分析モードの収集に対するチェックポイント永続化・レジューム・部分成功出力・シグナル対応」に限定する。以下は対象外とする。

- **結合エクスポートモード（`cli.py`）の中断耐性**: 別 spec で扱う。本 spec の永続化基盤は将来流用できるよう配慮するが、結合モードへの適用実装は行わない。
- **fsexport のレジューム・差分同期**: 0004/0005 で実装済み。本 spec では扱わない。
- **収集のストリーミング化による抜本的メモリ枯渇対策**: `Collector.collect()` のジェネレータ化・2 パス集計は将来 spec とする。本 spec は収集済みデータをメモリに保持する現行構造を前提に、永続化で「中断時の損失」を防ぐことに限定する。
- **チェックポイントを跨いだ差分同期（前回分析との差分抽出）**: 本 spec のチェックポイントは「1 回の分析の中断再開」のための機構であり、過去の分析結果との差分比較・増分分析は対象外。
- **分析エンジン・JSON スキーマ骨格・Skill/MCP 枠組みの作り直し**: 0007/0008 を再利用し、追加のみで実装する。
- **数値性能目標**: 想定最大ページ数・許容実行時間の数値目標は設けない。flush 粒度・部分出力・レジュームで損失と再実行コストを抑える。
