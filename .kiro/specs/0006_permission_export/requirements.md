# Requirements Document

## はじめに

本機能は、Confluence のページに設定されたアクセス権限（コンテンツ制限）を取得し、**Markdown として出力する**機能を C2M-Export に追加するものである。具体的には、各ページに対して「誰に Read 権が、誰に Read+Write 権が与えられているか」（ユーザー・グループ）を人間が読める形で記録する。

本機能の目的は、Confluence からエクスポートしたコンテンツを SharePoint / OneDrive をはじめとする各種配置先へ移行した後、**管理者が同等のアクセス設定を再適用する際の参照情報を提供する**ことにある。本機能は Confluence 側の権限を「記録・出力」するにとどまり、配置先への権限の自動適用は行わない（対象外）。再適用は管理者の手作業または別ツールの責務とする。

本機能はファイルシステムエクスポート（`0004_filesystem_export`）と並行して動作しうるが、権限情報の取得・出力は独立性が高いため別 spec（C）として切り出す。先行する分析 spec（`0003_confluence_assessment`）では権限の「件数・登場する関係者の集計」までを扱っており、本 spec は各ページの権限内容そのものの Markdown 出力を担う。権限取得には 0003 で追加予定の `ConfluenceClient.get_restrictions`（Data Center の `/rest/api/content/{id}/restriction/byOperation`）を再利用する。

既存の結合モード（`cli.py`）および 0004 の基本エクスポートの挙動は変更せず、オプトインで有効化する機能として追加する。すべてのログ・ドキュメントは日本語とし、姉妹プロジェクト（J2M-Export / G2M-Export）との一貫性、将来の Confluence Cloud 対応を見据えた拡張性を維持する。

### 分割方針における本 spec の位置づけ

0003 のスコープ外とした後続機能のうち、本 spec は C を担う。

- A（`0004_filesystem_export`）: ページ階層のファイルシステム出力、添付 DL、Frontmatter、リンク書き換え。
- B（`0005_resume_and_sync`）: 中断再開と差分同期。
- **C（本 spec / 0006）**: アクセス権限情報の Markdown 化と格納。A と並行だが独立。

### 用語

- **コンテンツ制限（restriction）**: Confluence のページに設定された Read / Read+Write のアクセス制限。
- **Read 権**: 閲覧のみが許可された対象（ユーザー/グループ）。Confluence API の操作キー `read` に相当。
- **Read+Write 権**: 閲覧と編集が許可された対象。Confluence API の操作キー `update` に相当（本 spec では「Read+Write」と表現する）。
- **継承**: ページが個別のコンテンツ制限を持たず、親から制限を引き継いでいる（または制限なしの）状態。
- **権限レポート**: 本機能が出力する、ページと権限の対応を記録した Markdown。
- **配置先**: エクスポート結果の最終的な保存・共有先（SharePoint / OneDrive 等、特定サービスに限定しない）。

### 未確定事項（設計フェーズで決定する）

- 権限レポートの格納形態（トップレベルの俯瞰ファイルに集約するか、各ページ対応ディレクトリに分散配置するか。既定はトップレベル集約を想定）。
- ユーザー/グループの識別子表現（Data Center の `username` + `displayName`、グループ名）と、配置先アカウントとの突き合わせを容易にする形式。
- 権限レポートの対応付けキー（page_id / 相対パス / タイトル）と、0004 の出力ディレクトリ構造との紐付け方法。
- 機械可読形式（JSON 等）の併用要否。

## 要件

### 要件 1: 権限情報の取得

**ユーザーストーリー:** 管理者として、各ページに設定された Read / Read+Write の権限（ユーザー・グループ）を取得したい。

#### 受け入れ基準

1. THE システム SHALL 各ページのコンテンツ制限を Confluence API（Data Center の `/rest/api/content/{id}/restriction/byOperation`）から取得する。
2. THE システム SHALL 取得結果を Read 権（操作キー `read`）と Read+Write 権（操作キー `update`）に区別する。
3. THE システム SHALL Read / Read+Write それぞれについて、許可されたユーザーとグループを列挙する。
4. THE システム SHALL 権限取得に既存クライアントの認証（Bearer）・Proxy・リトライ方針を適用する。
5. THE システム SHALL 大量ページに対する取得で、必要に応じたページング・負荷抑制を行う（方式は設計で確定）。

### 要件 2: 対象範囲の指定

**ユーザーストーリー:** 管理者として、特定ページ配下または Space/Workspace 全体の権限をまとめて取得したい。

#### 受け入れ基準

1. WHEN ルートページ ID が指定される THEN システム SHALL そのページを起点に子孫ページを巡回して権限を取得する。
2. WHEN 複数のルートページ ID が指定される THEN システム SHALL それぞれを順次処理する。
3. WHEN Space キーが指定される THEN システム SHALL その Space 内のトップレベルページを起点に巡回する。
4. THE システム SHALL 0004 / 0005 と一貫した起点指定（`root_page_ids` / `space_keys`）を用いる。

### 要件 3: 継承・制限なしの区別

**ユーザーストーリー:** 管理者として、ページに個別の制限が設定されているのか、親から継承している（または制限なしの）のかを区別して把握したい。

#### 受け入れ基準

1. WHERE ページが個別のコンテンツ制限を持つ THE システム SHALL その制限内容（Read / Read+Write の保有者）を記録する。
2. WHERE ページが個別のコンテンツ制限を持たない THE システム SHALL それを「制限なし/継承」として明示的に区別して記録する。
3. THE システム SHALL 継承の扱いとして、親をさかのぼった実効権限の展開は行わず、個別制限を持たないページは「継承/制限なし」と記すにとどめる。これにより、個別に権限が設定された箇所（＝管理者が意図的に権限を操作した箇所）を浮かび上がらせる。
4. THE システム SHALL 上記の継承方針（実効権限を展開しないこと）をドキュメントで明示する。

### 要件 4: 権限レポートの出力（Markdown）

**ユーザーストーリー:** 管理者として、ページと権限の対応を人間が読める Markdown で受け取り、移行後の権限再設定の作業リストとして使いたい。

#### 受け入れ基準

1. THE システム SHALL ページと権限（Read / Read+Write の保有者）の対応を Markdown として出力する。
2. THE システム SHALL 権限レポートの格納形態を設定で選択可能にする。既定はトップレベルの俯瞰ファイル（出力全体でどのページにどの権限が付与されているかを一覧できる集約ファイル）とし、各ページ対応ディレクトリへの分散配置も選択可能とする（既定・選択肢は設計で確定）。
3. THE 権限レポート SHALL 各ページを識別できる情報（page_id、タイトル、Confluence URL、該当する場合はローカル相対パス）を含む。
4. THE システム SHALL Read 権と Read+Write 権を明確に区別して表示する。
5. THE システム SHALL ユーザー/グループを、配置先アカウントとの突き合わせがしやすい識別子（ユーザー名・表示名、グループ名）で記載する。
6. THE システム SHALL 権限レポートを UTF-8 で書き込む。
7. THE システム SHALL （任意）機械可読形式（JSON 等）での併用出力を設けられる余地を残す（優先度は設計で確定）。
8. THE システム SHALL 本機能が Confluence 側権限の記録であり、配置先への自動適用ではないことをレポート内に明示する。

### 要件 5: 0004 / 0005 との関係と独立実行

**ユーザーストーリー:** 利用者として、権限エクスポートを単独でも、ファイルシステムエクスポートと組み合わせても使いたい。既存の挙動は壊さないでほしい。

#### 受け入れ基準

1. THE システム SHALL 権限エクスポートを設定（CLI 引数 / YAML）でオプトインとして有効化する。
2. WHEN 権限エクスポートを指定しない THEN システム SHALL 0004 のファイルシステム出力および結合モードの挙動を変更しない。
3. WHERE 0004 と併用される THE システム SHALL 権限レポートのローカル相対パスを 0004 の出力ディレクトリ構造と対応付ける。
4. WHERE 単独で実行される THE システム SHALL 0004 の本文・添付出力を必須とせず、権限レポートのみを出力できる。
5. THE システム SHALL 本機能の設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決する。
6. THE システム SHALL 既存の結合モード（`cli.py`）の挙動を一切変更しない。

### 要件 6: 部分成功・継続とエラーハンドリング

**ユーザーストーリー:** 管理者として、一部ページの権限取得に失敗しても全体が止まらず、何が取得できなかったか把握したい。

#### 受け入れ基準

1. IF あるページの権限取得に失敗した THEN システム SHALL そのページをスキップせず本文処理とは独立に扱い、権限取得の失敗を集計して継続する。
2. THE システム SHALL 権限取得に失敗したページの件数と対象（page_id）を集計・報告する。
3. THE システム SHALL 権限取得失敗を Confluence 側の一時的事象（権限不足・ネットワーク）と区別できるよう、失敗理由を日本語で記録する。
4. THE システム SHALL エラーメッセージを「現象・原因・対処方法」の構成で日本語出力する。

### 要件 7: 大規模ワークスペースへの対応

**ユーザーストーリー:** 管理者として、大量ページでも権限取得が現実的な時間・負荷で完了してほしい。

#### 受け入れ基準

1. THE システム SHALL 子ページ一覧の取得をページング処理で全件取得する（既存方針を踏襲）。
2. THE システム SHALL サーバーエラー（5xx）・ネットワークエラーに対し指数バックオフでリトライする（既存方針を踏襲）。
3. THE システム SHALL 権限取得の進捗（処理済みページ数）を日本語ログで定期的に報告する。
4. THE システム SHALL API 呼び出し回数を抑制する（`byOperation` で read/update を一括取得する等）。

### 要件 8: ログ・ドキュメント・設定・サマリの一貫性

**ユーザーストーリー:** 利用者として、既存ツールと一貫した日本語ログ・サマリで権限エクスポートを使いたい。

#### 受け入れ基準

1. THE システム SHALL すべてのログ出力を日本語で行う。
2. THE システム SHALL 処理完了時に、権限を出力したページ数・個別制限ありページ数・継承/制限なしページ数・取得失敗件数を含むサマリを出力する。
3. THE システム SHALL サマリを標準出力（ログ）に加え、実行日時（年月日・時分秒。ミリ秒は不要）をサフィックスに付したサマリファイルとしても出力する（0004 / 0005 のサマリ方針と整合）。
4. THE システム SHALL 新しい設定キーのサンプルを `c2m_config_sample.yaml` に追加する。
5. THE システム SHALL 既存の `--base-url` / `--proxy` / `--token` / `--output-dir` 等の引数を踏襲し、ベース URL を末尾スラッシュ削除（rstrip）で正規化する。
6. WHEN 本機能を追加する THEN システム SHALL `README.md` および `README_DEV.md` を更新する。
7. THE システム SHALL コード内コメント・docstring を日本語（PEP 257 準拠）で記載する。
8. WHERE Web UI（Streamlit）への露出が要求される THE システム SHALL 本機能をバックエンドロジックとして安全に呼び出せる形で提供する（露出範囲は設計で確定）。

## スコープ外（他 spec で扱う / 対象外）

- **配置先（SharePoint / OneDrive 等）への権限の自動適用**: 対象外。本機能は Confluence 側権限の記録・出力までを担い、再適用は管理者の手作業または別ツールの責務とする。
- **Confluence 側権限の変更・付与・剥奪**: 対象外。読み取り専用で取得する。
- **Space レベルの権限（スペース権限）やグローバル権限の網羅的エクスポート**: 本 spec はページのコンテンツ制限を主対象とする（スペース権限の扱いは設計で要否を検討）。
- **権限情報の差分同期**: 権限の変化を追跡する差分同期は、B（0005）の仕組みが確定した後に別途検討する（本 spec では毎回取得・出力する前提）。
- **ページ本文・添付のファイルシステム出力**: A（0004）が担う。
