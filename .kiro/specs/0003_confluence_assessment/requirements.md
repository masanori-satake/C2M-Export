# Requirements Document

## はじめに

本機能は、Confluence のコンテンツ（特定ページ配下、または Workspace/Space 全体）を実際にエクスポートする前に、**その規模・構造・移設リスクを把握するための分析（アセスメント）機能**を C2M-Export に追加するものである。

利用者の実際のワークフローは次の 3 段階からなる。

1. **分析（本 spec のスコープ）**: Confluence のワークスペース全体の概要を把握し、規模・構造・移設上のリスクを詳細に分析する。
2. **ルール決定**: 分析結果をもとに、何をエクスポートし何を除外するか、どのサイズ上限・ディレクトリ命名規約を用いるか等のルールを決める。
3. **エクスポート実行（後続 spec のスコープ）**: 決めたルールに従い、ページ階層・添付・権限情報をファイルシステムへ出力する。

本 spec は上記 1 の「分析」に主眼を置く。実際のファイルシステムへのエクスポート出力、添付ファイルのダウンロード、中断再開（レジューム）・差分同期（追加・変更・削除の反映）、アクセス権限のエクスポートは、本機能の分析結果を前提とする**後続 spec**で扱う（本書末尾の「スコープ外（後続 spec で扱う）」を参照）。

分析は Confluence REST API のメタデータ（添付ファイルの `fileSize`、ページの `version` / `lastModified`、コンテンツ制限等）をベースに行い、**添付ファイルのバイナリ本体はダウンロードしない**軽量な方式とする。想定する移設先は SharePoint / OneDrive であり、分析ではこれらの移設先固有の制約（パス長・禁止文字・ブロック拡張子等）に起因するリスクも検出する。

本機能は既存の結合 Markdown エクスポートの挙動を一切変更せず、新たなサブコマンド/モードとして追加する。姉妹プロジェクト（J2M-Export / G2M-Export）との CLI 引数・振る舞いの一貫性、および将来の Confluence Cloud 対応を見据えた拡張性を維持する。

### 用語

- **分析 / アセスメント**: 実際の書き込み・ダウンロードを行わず、Confluence コンテンツの規模・構造・移設リスクを調査・集計すること。
- **添付ファイル（attachment）**: Confluence のページに添付されたドキュメント・画像等のバイナリ。
- **移設先**: 本機能が想定する出力先。主に SharePoint / OneDrive。
- **分析レポート**: 分析結果をまとめた成果物。人間可読な Markdown と機械可読な JSON の両形式で出力する。
- **コンテンツ制限（restriction）**: Confluence のページに設定された Read / Read+Write のアクセス制限。

### 未確定事項（設計フェーズで決定する）

- Workspace/Space 全体を対象とする場合の起点列挙 API（Space 内トップレベルページの列挙方式）。
- 添付サイズ・ページ更新情報・権限を取得する具体的な API エンドポイントと expand パラメータ。
- SharePoint のパス長・禁止文字・ブロック拡張子の具体的な判定基準値（既定値のソースと根拠）。
- 大規模ワークスペースにおける API 呼び出し回数の抑制方法（並列度・ページング・レート制御）。

## 要件

### 要件 1: 分析モードの提供と既存挙動の非破壊

**ユーザーストーリー:** 利用者として、既存の結合 Markdown エクスポートとは別に「分析のみを行うモード」を使いたい。既存機能の挙動は変わらないでほしい。

#### 受け入れ基準

1. THE システム SHALL 実際のエクスポート出力とは独立して起動できる分析モード（サブコマンドまたは専用フラグ）を提供する。
2. WHEN 分析モードが実行される THEN システム SHALL ファイルの書き込み（分析レポートを除く）および添付バイナリのダウンロードを一切行わない。
3. WHEN 利用者が分析モードを指定しない THEN システム SHALL 既存の結合 Markdown エクスポートの挙動を変更しない（後方互換）。
4. THE システム SHALL 分析モードの設定を既存の優先順位（CLI 引数 > 環境変数 > YAML > デフォルト）で解決する。
5. THE システム SHALL 既存クライアントの認証（Bearer）・Proxy・リトライ方針を分析モードでも適用する。

### 要件 2: 分析対象範囲の指定

**ユーザーストーリー:** 利用者として、特定ページ配下だけでなく Workspace（Space）全体を分析対象に指定したい。

#### 受け入れ基準

1. WHEN ルートページ ID が指定される THEN システム SHALL そのページを起点に子孫ページを DFS で巡回して分析する。
2. WHEN 複数のルートページ ID が指定される THEN システム SHALL それぞれを順次分析し、結果を統合する。
3. WHEN Space キーが指定される THEN システム SHALL その Space 内のトップレベルページを列挙し、各々を起点に分析する。
4. WHERE Workspace 全体（複数 Space）の分析が要求される THE システム SHALL 対象 Space の集合を指定できる手段を提供する（具体的な指定方法は設計で確定）。
5. IF 指定された起点（ページ ID / Space キー）が存在しない、または権限がない THEN システム SHALL 現象・原因・対処方法を日本語で報告する。

### 要件 3: 規模・構造の分析

**ユーザーストーリー:** 利用者として、エクスポートした場合のファイル数・総データサイズ・階層の深さといった全体規模を把握し、単一の格納先で足りるか、複数の格納先が必要か、あるいは見送るかを判断したい。

#### 受け入れ基準

1. THE システム SHALL 総ページ数を集計する。
2. THE システム SHALL 総添付ファイル数を集計する。
3. THE システム SHALL 推定総サイズを集計する（ページ本文の概算 + 添付のメタサイズ合計）。
4. THE システム SHALL 階層の最大深さと、階層レベル別のページ数分布を集計する。
5. WHERE 複数 Space が対象 THE システム SHALL Space 別のページ数・添付数・推定サイズを集計する。
6. THE システム SHALL 添付サイズを API メタデータ（`extensions.fileSize` 等）から取得し、バイナリをダウンロードせずに合計する。
7. THE システム SHALL ページ本文の推定サイズを軽量な方式（Storage Format の生サイズまたは簡易換算）で概算する。
8. IF メタデータにサイズ情報が欠落している添付が存在する THEN システム SHALL その件数を報告し、見積りの不確実性として明示する。

### 要件 4: 添付ファイルの種別分析

**ユーザーストーリー:** 利用者として、添付ファイルを拡張子（タイプ）別に集計し、どの種類のドキュメントがどれだけの個数・容量を占めるかを把握したい。

#### 受け入れ基準

1. THE システム SHALL 添付ファイルを拡張子別に分類する。
2. THE システム SHALL 拡張子別に、個数・合計サイズ・最大サイズを集計する。
3. THE システム SHALL 拡張子を持たない添付、または拡張子が判別できない添付を区別して集計する。
4. THE システム SHALL 拡張子別集計をサイズまたは個数で降順に並べて報告する。
5. WHERE MIME タイプ情報が API から取得可能 THE システム SHALL 拡張子に加え MIME タイプ別の集計も行う（取得可否は設計で確定）。

### 要件 5: 移設リスク・制約の検出（SharePoint / OneDrive 向け）

**ユーザーストーリー:** 利用者として、Confluence から SharePoint / OneDrive へ移設する際につまずきそうな箇所を事前に洗い出し、ルール決定時の対処方針を立てたい。

#### 受け入れ基準

1. THE システム SHALL エクスポート時に想定されるファイルシステム上の相対パスを各ページ/添付について算出し、長さが移設先のパス長上限（既定値は設計で確定）を超える見込みの項目を検出・一覧化する。
2. THE システム SHALL ページタイトルまたは添付ファイル名に、移設先で禁止される文字（例: `" * : < > ? / \ |` 等）を含む項目を検出・一覧化する。
3. THE システム SHALL 予約語・末尾ドット/スペース等、移設先で問題となりうる名前を検出・一覧化する。
4. THE システム SHALL 単体で巨大な添付（設定可能な単一ファイルサイズ閾値を超えるもの）を検出・一覧化する。
5. THE システム SHALL 移設先がブロックする拡張子（例: 実行ファイル等、既定リストは設計で確定）の添付を検出・一覧化する。
6. THE システム SHALL 同一階層における同名ページ/同名添付の衝突が起きうる箇所を検出・一覧化する。
7. THE システム SHALL 各リスク項目について、対象（ページ ID / 添付名 / パス）と理由を特定できる情報を報告に含める。
8. THE システム SHALL 移設先固有の判定基準値（パス長上限・禁止文字・ブロック拡張子）を設定で上書き可能にする。

### 要件 6: 権限・移設計画の分析

**ユーザーストーリー:** 管理者として、移設後にアクセス権限を再設定する必要がある箇所の規模と、権限に登場する関係者を事前に把握したい。

#### 受け入れ基準

1. THE システム SHALL 個別のアクセス制限（コンテンツ制限）が設定されているページ数を集計する。
2. THE システム SHALL 制限に登場するユニークなユーザー/グループの一覧を収集する。
3. THE システム SHALL 権限を Read 権と Read+Write 権に区別して集計する。
4. WHERE ページが親から権限を継承しているのみで個別制限を持たない THE システム SHALL それを「制限なし/継承」として区別する。
5. IF 権限情報の取得に失敗した THEN システム SHALL 分析を中断せず、取得失敗の件数を日本語で報告する。
6. THE システム SHALL 権限分析の有効/無効を設定で切り替え可能にする（大規模時の API 負荷を考慮）。

### 要件 7: 鮮度・棚卸しの分析

**ユーザーストーリー:** 利用者として、長期間更新されていないページや空に近いページを把握し、移設対象から外す（捨てる）判断材料にしたい。

#### 受け入れ基準

1. THE システム SHALL 各ページの最終更新日（`version.when` / `lastModified` 等）を取得し、更新日の分布（期間別の件数等）を集計する。
2. THE システム SHALL 一定期間以上更新されていないページ数を、設定可能なしきい値に基づき集計する。
3. THE システム SHALL 本文が空、または極端に小さいページの件数を集計する。
4. THE システム SHALL 鮮度分析の基準（経過日数しきい値・最小サイズ）を設定で変更可能にする。

### 要件 8: 分析レポートの出力（Markdown + JSON）

**ユーザーストーリー:** 利用者として、分析結果を人間が読める形式で確認しつつ、別ツールやスクリプトで加工できる機械可読形式でも受け取りたい。

#### 受け入れ基準

1. THE システム SHALL 分析結果を人間可読な Markdown レポートとして出力する。
2. THE システム SHALL 分析結果を機械可読な JSON として出力する。
3. THE Markdown レポート SHALL 規模サマリ・添付種別集計・移設リスク一覧・権限サマリ・鮮度サマリの各セクションを含む。
4. THE JSON SHALL 集計値および検出された個別リスク項目を、キーが安定した構造化データとして含む。
5. THE システム SHALL サイズを人間が読みやすい単位（MB/GB 等）で Markdown に表示する。
6. THE システム SHALL 出力先ディレクトリ/ファイル名を設定で指定可能にし、未指定時は既定の命名規約で出力する。
7. WHEN 出力先に既存のレポートが存在する THEN システム SHALL 上書き可否を既存方針（`overwrite` 相当）に従って扱う。
8. THE システム SHALL 分析が概算（メタデータベース）であり厳密な実測値ではないことをレポート内に明示する。

### 要件 9: 大規模ワークスペースへの対応

**ユーザーストーリー:** 利用者として、大量のページ/添付を持つワークスペースでも、分析が現実的な時間・負荷で完了してほしい。

#### 受け入れ基準

1. THE システム SHALL 子ページ・添付一覧の取得をページング処理で全件取得する（既存方針を踏襲）。
2. THE システム SHALL サーバーエラー（5xx）・ネットワークエラーに対し指数バックオフでリトライする（既存方針を踏襲）。
3. THE システム SHALL 分析の進捗（処理済みページ数等）を日本語ログで定期的に報告する。
4. IF 個別ページの情報取得に失敗した THEN システム SHALL そのページをスキップし、分析を継続し、スキップ件数と ID を集計・報告する。
5. THE システム SHALL API 呼び出し回数を抑制する手段（必要な expand の最小化等）を設計で検討する。

### 要件 10: ログ・ドキュメント・設定の一貫性

**ユーザーストーリー:** 利用者として、既存ツールと一貫した操作感・日本語ログで分析機能を使いたい。

#### 受け入れ基準

1. THE システム SHALL すべてのログ出力を日本語で行う。
2. THE システム SHALL エラーメッセージを「現象・原因・対処方法」の構成で出力する。
3. THE システム SHALL 分析完了時に、総ページ数・総添付数・推定総サイズ・検出リスク件数・スキップ件数を含むサマリを出力する。
4. THE システム SHALL 新しい設定キーのサンプルを `c2m_config_sample.yaml` に追加する。
5. THE システム SHALL 既存の `--base-url` / `--proxy` / `--token` / `--output-dir` 等の引数を踏襲する。
6. THE システム SHALL Confluence のベース URL を末尾スラッシュ削除（rstrip）で正規化する既存方針を維持する。
7. WHEN 本機能を追加する THEN システム SHALL `README.md` および `README_DEV.md` を更新する。
8. THE システム SHALL コード内コメント・docstring を日本語（PEP 257 準拠）で記載する。
9. WHERE Web UI（Streamlit）への露出が要求される THE システム SHALL 分析機能をバックエンドロジックとして安全に呼び出せる形で提供する（露出範囲は設計で確定）。

## スコープ外（後続 spec で扱う）

本 spec は「分析」に限定する。以下は分析結果を前提とする後続 spec で扱う。

- ページ階層のファイルシステム（ディレクトリ/ファイル）への実エクスポート出力。
- 添付ファイルのバイナリダウンロードと保存（添付用サブディレクトリ名の設定化を含む）。
- 単一ファイルサイズ上限に基づく実エクスポート時のスキップ制御。
- 中断からの再開（レジューム）と、前回取得以降の差分（追加・変更・削除）を反映する差分同期（マニフェスト管理）。
- アクセス権限情報の Markdown 化と格納（本 spec では件数・関係者の集計のみを行い、権限内容そのものの出力は後続で扱う）。
- SharePoint / OneDrive への権限の自動適用（対象外。管理者の手作業または別ツールの責務）。
