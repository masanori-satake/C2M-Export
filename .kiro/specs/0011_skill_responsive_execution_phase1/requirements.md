# Requirements Document

## はじめに

本機能は、分析モードを Agent Skill（GitHub Copilot / Kiro 等）経由で実行した際の**応答性改善フェーズ 1**である。PR #69 で `--timeout-seconds` / `--max-pages`（実行保護リミット）と Windows 実行配慮が入ったが、2026-11-05 の実利用で、スキル経由の実行が長いとき10分以上「無応答に見える」状態になった。

原因は対象規模そのものよりも実行経路の設計にある:

- エージェントのターミナル実行はブロッキングであり、プロセス終了まで中間出力がエージェントに届かない。stderr の進捗ログだけでは「止まっていないこと」を伝えきれない場面があるが、少なくともターミナル表示とログの観点で無音区間をなくすことはできる。
- 補助スクリプト `run_analysis.py` は子プロセスをバッファリングありで起動しており、進捗ログの到着が遅れる。
- 進捗ログが件数ベース（10件ごと）のみで、本走査前の前段フェーズ（Space 一覧取得・起点解決・ワークスペース概要収集）には進捗が一切ない。遅いページが続く区間では進捗間隔自体が分単位になる。
- リトライ時の待機時間がログに出ず、何秒止まっているのか分からない。
- `--timeout-seconds` は既定が無制限で、スキル側も「推奨」止まりだったため、ガードレールが発動しないまま走り続けた。

本フェーズは「小変更・即効」に絞る。以後のフェーズ（フェーズ 2: 事前見積もり `--estimate`、フェーズ 3: 非同期 start/status/result プロトコル、フェーズ 4: 収集の高速化）は別 spec とする。人間向け CLI の同期実行と「stdout は純粋な JSON」という既存契約は変更しない。

### 用語

- **ハートビート**: 時間ベースで周期的に出力する生存ログ。現在のフェーズ名・経過秒数・（取得可能な場合）収集済み件数を含む。
- **スキル経由実行**: `skills/confluence-analysis/scripts/run_analysis.py`（および `.github/skills/`・`.kiro/skills/` の複製）を経由する実行。直接の CLI 実行と区別する。

## 要件

### 要件 1: スキル経由実行への実行時間上限の既定

**ユーザーストーリー:** スキル利用者として、上限を指定し忘れても分析が無制限に走り続けないようにしたい。

#### 受け入れ基準

1. THE 補助スクリプト SHALL `--timeout-seconds` が明示されていない場合、既定値 **300 秒** を補って子プロセスを起動する。
2. THE 補助スクリプト SHALL `--timeout-seconds <値>` 形式と `--timeout-seconds=<値>` 形式の両方を明示指定として扱い、その場合は既定値を補わない。
3. 上限到達時の振る舞い（収集済みデータでの partial 出力と `--resume` による再開）は PR #69 の実装をそのまま利用する。

### 要件 2: 無バッファ実行

**ユーザーストーリー:** 利用者として、進捗ログがバッファに溜まらず即時に流れてくるようにしたい。

#### 受け入れ基準

1. THE 補助スクリプト（analysis / tree の両スキル、全配置） SHALL 子プロセスを `python -u`（無バッファモード）で起動する。

### 要件 3: 時間ベースの進捗ハートビート

**ユーザーストーリー:** 利用者として、どのフェーズでも一定時間ごとに「まだ動いている」ことが分かるようにしたい。

#### 受け入れ基準

1. THE システム SHALL `run_analysis` の実行中、5 秒間隔でハートビートログ（フェーズ名・経過秒数）を stderr に出力する。
2. THE ハートビート SHALL フェーズ遷移（Space 一覧取得 / 起点解決 / ワークスペース概要収集 / ページ収集 / Space 詳細収集 / 集計・結果構築）を反映し、ページ収集フェーズでは収集済み件数を併記する。
3. THE システム SHALL 前段フェーズにも開始ログを出力する（従来は無言だった区間）。
4. THE ハートビート SHALL 正常終了・エラー終了のいずれでも確実に停止する（スレッドを残さない）。

### 要件 4: リトライ待機時間の可視化

**ユーザーストーリー:** 利用者として、API リトライで止まっているときに何秒待っているのか知りたい。

#### 受け入れ基準

1. THE Confluence クライアント SHALL リトライ時に待機秒数を含む警告ログを出す（5xx リトライと通信エラーリトライの両方）。

### 要件 5: 後方互換

#### 受け入れ基準

1. THE CLI SHALL stdout に純粋な JSON のみを出力する契約を維持する（ハートビート・フェーズログは stderr）。
2. THE 直接の CLI 実行 SHALL 従来どおり上限なしを既定とし、本フェーズで既定値を強制しない（既定 300 秒はスキル経由にのみ適用する）。
3. THE JSON スキーマ（schema_version 1.2）SHALL 変更しない。
